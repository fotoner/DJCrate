# rekordbox 7 내부 형식 — DJCrate가 알아낸 쓰기 규칙

이 문서는 DJCrate가 rekordbox 7.2.18 실험으로 알아낸 쓰기 규칙이다. 사용자가 rekordbox에서 직접 편집한 결과를 스냅샷끼리 diff해서 뽑았다.

규칙마다 아래 방법으로 확인했다.

1. 실험 전 사본에 DJCrate로 같은 편집을 쓴다.
2. rekordbox가 쓴 결과와 칸마다 비교한다.

확인하지 못한 규칙은 코드에서 막아 두었다. 목록은 아래 "막아 둔 것"에 있다.

코드는 `Sources/RekordboxKit/`에 있다.

| 타입 | 맡는 일 |
|---|---|
| `RekordboxWriter` | DB 쓰기. 역할별 파일은 `+Cues`·`+Grid`·`+Gain`·`+Analysis`·`+Tags`·`+Artwork`·`+Playlist`·`+Verify`·`+Backup` |
| `RekordboxGridWriter` | ANLZ 쓰기 |
| `RekordboxCompatibility` | 쓰기 전 버전·구조 확인 |
| `CueJSON`, `AnlzFile`, `SeekInfo`, `MasterPlaylistsXML`, `CipherDatabase` | 함께 쓰는 타입 |

## 파일과 열기

- 라이브러리는 SQLCipher 4 형식의 `~/Library/Pioneer/rekordbox/master.db`이다.
- 키는 pyrekordbox와 같은 방식으로 푼다(`RekordboxKey.derive()`).
- 분석 파일은 `~/Library/Pioneer/rekordbox/share/PIONEER/USBANLZ/<3자리>/<uuid 나머지>/ANLZ0000.{DAT,EXT,2EX,3EX}`이다.
- 분석 파일 경로는 `djmdContent.AnalysisDataPath`에 `.DAT` 경로로 들어 있다.
- 행의 절반쯤은 삭제 행이다(`rb_local_deleted=1`). 집계와 쓰기는 늘 삭제되지 않은 행만 본다.
- `agentRegistry`에는 클라우드 인증값이 있으므로 이 값은 읽지도 출력하지도 않는다.
- `djc lab sql`은 이 표의 질의를 막는다.
- 예외로, 쓰기 모듈은 `localUpdateCount`를 읽어서 고쳐 쓴다. `lastUpdateCount`는 정수 칸만 읽는다.

### iTunes 동기화 목록 읽기 (2026-09-27, #100)

**목록의 성격**

- iTunes 아래의 동기화 목록은 일반 `djmdPlaylist` 목록과 구분한다.
- 목록 구성과 순서는 읽기 전용이다.
- 컬렉션에 든 곡의 큐와 태그는 기존 rekordbox 곡에 연결해야 한다.

**동기화 파일**

- rekordbox 폴더의 `playlists3.sync`는 `SYNC_ITUNES_PLAYLIST/PLAYLISTS/NODE` XML이다.
- `Lib_Type="1"` 노드에는 이름과 곡 목록 없이 아래 속성만 있다.

| 속성 | 뜻 |
|---|---|
| `Id` | iTunes 영구 ID |
| `ParentId` | 부모 ID |
| `Attribute` | 폴더 여부: 1 폴더·0 목록 |
| `CheckType="1"` | 동기화 선택 |

- ID는 앞의 0을 생략한 UInt64 16진수다.
- `rekordbox6/rekordbox3.settings`의 `showAllItunesPlaylist="0"`은 rekordbox 화면이 동기화 목록만 보이는 상태와 일치했다.
- `MusicAppLoadingType="1"`인 환경에서 동기화 ID를 Apple `ITLibrary` API와 대조해 목록과 곡 순서를 확인했다.
- 일반 DB에서는 그 목록 이름을 찾지 못했다.

**읽는 방식**

- 공식 개발진은 Framework 방식을 이렇게 설명한다([공식 답변](https://forums.pioneerdj.com/hc/en-us/community/posts/900001887506-What-does-Framework-in-iTunes-load-method-mean-and-imply-for-the-sync-manage)).
  - Framework 방식은 Apple의 `ITLibrary`에서 Music 보관함 정보를 읽는다([Apple API](https://developer.apple.com/documentation/ituneslibrary/itlibrary)).
  - 사용자는 이 방식과 XML 방식 중 하나를 고를 수 있다.
- 동기화 선택 정보가 있다고 해서 마지막 동기화 때의 이름과 곡 순서가 별도 DB에 남는다고 가정하지 않는다.
- DJCrate는 동기화 ID로 보일 목록을 고른다.
- DJCrate는 선택 창에서 고른 목록을 바꿀 수 있게 전체 목록 본문도 사본에 보관한다.
- 읽기는 rekordbox 설정을 따른다(`RekordboxITunesReader`).
  - Framework 방식은 `ITLibrary`를 읽는다.
  - XML 방식은 설정의 `itunesLibraryFile`을 읽는다.
- 실제 화면에서 아래를 확인했다.
  - Framework를 고른 상태와 설정값 1
  - 동기화 파일과 API의 목록 순서
  - 화면에 보인 목록의 기존 컬렉션 연결
- XML 방식(값 0)은 합성 설정과 XML로 검증했다.

**목록 사본**

- DJCrate는 앱 시작, 새 스냅샷, iTunes 목록 새로고침 때 목록을 읽는다.
- 읽은 목록은 `<DB 스냅샷>.itunes.json`에 사본으로 보관한다.
- 읽기에 실패하면 마지막 정상 사본을 덮어쓰지 않는다. 이때 현재 화면과 새 DB 스냅샷에는 이전 목록을 오래된 자료로 보인다.
- 직전 사본이 손상됐으면 같은 스냅샷 폴더에서 더 이른 정상 사본을 찾는다.
- 새 DB를 뜨기 전에 이전 목록을 메모리에 보관해, 같은 초에 파일 이름을 다시 써도 복구한다.
- 같은 DB의 갱신은 요청 순서로 채택한다. sidecar 확인과 저장은 한 잠금 안에서 끝낸다.
- 겹친 DB 스냅샷 생성은 순서대로 처리한다.
- 명시한 `--db`·`DJC_DB` 모드에서 iTunes 새로고침 버튼은 현재 DB와 그 옆의 목록 사본·동기화 파일만 다시 읽는다.
- 그 모드에서도 별도의 새 스냅샷 메뉴는 원래 동작을 따른다.
- 비어 있지 않은 `DJC_REKORDBOX_DIR` 사본도 그 폴더의 DB와 목록만 읽어 실제 Music 보관함과 섞지 않는다.
- 오래된 DB를 정리할 때 목록 사본도 지운다.

**컬렉션 곡 연결**

- `SyncedITunesLibrary`는 정규화한 파일 경로가 유일하게 일치하는 기존 컬렉션 곡만 연결한다(삭제 행 제외).
- 없는 곡과 모호한 경로는 개수를 알린다.
- 같은 곡의 반복과 원래 순번은 그대로 둔다.
- 행 ID는 목록 ID, 기존 곡 ID, 곡별 등장 순번으로 만든다.
- 편집은 기존 곡 ID로 연결한다.
- 별도 사이드바 항목과 `itunes:` ID를 써서 재생 목록 초안에 섞이지 않게 한다.
- 목록 구성, 순서, 삭제는 막는다.
- 기존 곡의 큐·태그 초안과 반영 경로는 그대로 쓴다.

### iTunes 동기화 선택 쓰기 (2026-09-27, rekordbox 7.2.14.0323)

**실험**: 실제 설치 버전 `7.2.14.0323`에서 사용자가 아래 순서로 편집한 전후 사본을 비교했다.

1. 고른 재생 목록 하나를 해제한다.
2. SYNC한다.
3. rekordbox를 종료한다.

**결과**

- `playlists3.sync`에서 그 목록의 NODE가 없어졌다.
- 상위 폴더의 `CheckType`은 1→2가 됐다.
- 남은 iTunes 노드의 `Timestamp`는 동기화 시점의 Unix 밀리초로 바뀌었다.
- 루트(ID 0)는 시각 0을 유지했다.
- 아래는 바뀌지 않았다.
  - 루트·PRODUCT 메타데이터
  - 남은 노드의 순서
  - `masterPlaylists6.xml`
  - iTunes 읽기·표시 설정
  - 인증 표를 뺀 DB의 표·행·칸(변화 없음)
- Music API의 폴더별 선행 순회는 파일의 노드 순서와 같았다.
- 같은 목록을 다시 체크해 SYNC하자 목록 NODE는 제자리로 돌아왔다. 그러나 부모의 `CheckType`은 **2를 유지**했다.
- 하위를 모두 고른 상태와 폴더 자체를 고른 상태는 다르다.

**사본 재현**

- `ITunesSyncExperimentRepro`는 전후 파일의 모든 NODE 속성과 순서를 사본에서 재현한다.
- 실행 시각은 전후 대조를 위해 주입한다.
- 실제 `RekordboxWriter.write` 경로도 사본에서 실행해, 시각 밖의 모든 칸·순서 일치와 DB 바이트 불변을 확인한다.
- 실제 파일은 저장소에 넣지 않는다.

**DJCrate가 쓰는 것**

- DJCrate도 부모를 직접 고를 때만 1, 하위 선택만 있으면 2로 쓴다.
- DJCrate는 ID 0을 `All Playlist`의 명시적인 선택으로 보아 따로 보존한다.
- 추가와 해제 두 방향 모두 속성과 순서 재현을 통과해 `RekordboxWriter.write(iTunesSync:)`를 열었다.
- 쓰기 순서는 아래와 같다.
  1. rekordbox 실행 여부와 버전을 검사한다.
  2. DB 구조와 카운터를 검사한다.
  3. 전체 DB와 동기화 파일을 백업한다.
  4. 선택 원문(base)을 다시 확인한다.
  5. 동기화 파일을 원자적으로 교체한다.
  6. 다시 읽어 무결성을 검사한다.
- DB와 Music 보관함에는 쓰지 않는다.
- 실패하면 동기화 파일을 복원한다.
- 그 뒤 외부에서 선택을 바꾸면, 되돌리기도 그 선택을 덮어쓰지 않는다.

**선택 읽기**

- DJCrate 전용 선택 파일은 더 이상 읽지 않는다.
- 선택의 기준은 `playlists3.sync`다.
- DB가 그대로인 동기화 변경도 창으로 돌아올 때 감지한다.
- 명시한 DB 사본에서는 그 옆 동기화 파일만 읽는다. 동기화 쓰기는 다른 쓰기와 같은 쓰기 대상에 한다.
- 읽기 요청 순서는 스냅샷 URL별로 관리한다.
- 동기화 쓰기 세대는 출처 DB별로 관리한다.
- 쓰기가 끝나면 같은 출처의 오래된 캡처와 화면 로드를 무효로 한다.
- 서로 다른 URL의 정상 캡처는 뒤의 갱신 실패 때 복구 자료로 쓰도록 각각 보존한다.
- `DJC_REKORDBOX_DIR`만 지정한 모드는 사본 루트의 현재 동기화 파일을 적용한다.
- 새 스냅샷을 뜰 때 같은 출처의 현재 목록도 메모리에 보관한다. 아래 경우에도 선택과 전체 목록이 옛 값으로 돌아가지 않게 하려는 것이다.
  - 같은 초에 파일명을 다시 씀
  - 루트 캐시가 없음
  - 루트 캐시가 오래됨
- 명시한 `--db`·`DJC_DB`는 기본 스냅샷 폴더 안에 있어도 자동으로 다른 DB를 열지 않는다.
- 선택 창은 `ITunesSyncOutline`으로 이름과 계층만 만든다.
- 곡 경로 정규화와 컬렉션 곡 연결은 실제 라이브러리 목록을 읽을 때만 한다.
- 선택 창의 화면 계산은 트리와 미리 보기를 한 번씩 만든다.

## 쓰기 전 확인 (`RekordboxCompatibility`)

쓰기 규칙은 rekordbox 7.2.18에서 확인했다. rekordbox가 업데이트로 DB 구조를 바꾸면 규칙이 맞지 않을 수 있으므로 쓰기 전에 아래 항목을 본다. 하나라도 다르면 **백업도 뜨지 않은 채** 쓰기를 막는다.

- **앱 버전**: `/Applications/rekordbox N/rekordbox.app`의 `CFBundleShortVersionString` 주.부가 `7.2`여야 한다. 앱을 못 찾으면 아래 DB 검사에 맡긴다. 앱 버전 검사는 라이브 DB에만 한다.
- **새 행을 넣는 표**: 칸 이름이 아래와 정확히 같아야 한다. 칸이 늘면 rekordbox가 기대하는 값을 빠뜨리게 된다.

  | 쓰기 | 표와 칸 수 |
  |---|---|
  | 큐 | `djmdCue` 29칸, `contentCue` 13칸 |
  | 곡 넣기 | `djmdContent`, `djmdArtist`, `djmdAlbum`, `djmdGenre` |
  | 곡 넣기·분석 붙이기 | `contentFile` 24칸, `djmdMixerParam` 15칸 |
  | 재생 목록 | `djmdPlaylist` 16칸, `djmdSongPlaylist` 13칸, `djmdCloudFilterPlaylist` 13칸 |

- **고치는 칸과 읽는 칸**: `agentRegistry`, `djmdProperty`, 곡 삭제의 `djmdSongHistory`에서 쓰는 칸이 모두 있어야 한다.
- **DB 버전**: `djmdProperty.DBVersion`이 `6000`이어야 한다.
- **카운터**: `localUpdateCount`가 클라우드 동기화가 본 가장 큰 번호 이상이어야 한다. 식은 `localUpdateCount` ≥ `lastUpdateCount`다.
  - 로컬 번호가 더 작을 때 동기화가 변경을 되돌린 사례가 있다(2026-09-26 조사).
  - 2026-09-26 실제 라이브러리 값은 로컬 1,002,950, 클라우드 372,628이었다.

`djc compat`으로 읽기 전용 확인을 할 수 있다. 새 rekordbox 버전을 허용하려면 아래 순서를 따른다.

1. "새 쓰기 경로를 여는 방법"처럼 실험으로 큐·그리드·게인 쓰기를 다시 확인한다.
2. `verifiedAppVersions`를 넓힌다.

## 공통: 변경 번호(usn)

- 바뀐 행마다 `rb_local_usn`에 `agentRegistry`의 `localUpdateCount`를 1씩 올린 값을 준다.
- 마지막 값은 `localUpdateCount`에 적는다.
- `rb_data_status`는 256 → 257로 바꾸되 이미 257이면 그대로 둔다.
- `updated_at` 모양은 `YYYY-MM-DD HH:MM:SS.sss +00:00`이다.
- 한 곡의 큐를 바꾸면 `contentCue`가 먼저, `djmdContent`가 그다음 번호를 받는다. 두 번호는 이어진다.

## 큐 (`djmdCue` + `contentCue`)

- 바꾼 큐는 행을 지운 뒤 새로 넣는다.
- 새 `ID`는 겹치지 않는 임의 UInt32를 문자열로 적는다. 새 `UUID`는 소문자 UUID다.
- `InMsec`은 ms, `InFrame`은 ms × 150 / 1000을 내림한 값이다.
- 루프가 아니면 `OutMsec`은 −1, `OutFrame`은 0이다.
- 루프가 아닌 새 큐는 아래 값을 쓴다.

  | 칸 | 값 |
  |---|---|
  | `Color` | −1 |
  | `ColorTableIndex`, `ActiveLoop`, `BeatLoopSize`, `CueMicrosec` | NULL |
  | `Comment` | 코멘트가 없으면 NULL |

- `Kind` 값은 아래와 같다.

  | `Kind` | 큐 |
  |---|---|
  | 0 | 메모리 큐 |
  | 1·2·3 | 핫큐 A·B·C |
  | 5~9 | 핫큐 D~H |
  | 4 | 뜻을 몰라 편집 대상에서 뺀다 |

- 메모리 큐는 자동 큐 "1.1Bars"를 포함해 곡당 10개까지다. 핫큐 칸은 곡당 하나씩이다.
- `contentCue.Cues`는 곡의 모든 큐를 담은 JSON 배열이다.
  - 옛 rekordbox가 쓴 칸 순서는 다르므로 원래 객체는 **읽은 칸 순서 그대로** 다시 쓴다.
  - 새 객체는 끝에 붙인다. 칸 순서는 `ID, ContentID, ContentUUID, InMsec, InFrame, InMpegFrame, InMpegAbs, InPointSeekInfo, OutMsec, OutFrame, OutMpegFrame, OutMpegAbs, OutPointSeekInfo, Kind, Color, ColorTableIndex, ActiveLoop, Comment, BeatLoopSize, CueMicrosec, UUID, created_at, updated_at`이다.
  - NULL 칸과 빈 코멘트(`""`)는 적지 않는다. 라이브러리 JSON에 `"Comment":""`는 0건이다.
  - 시각 모양은 `2026-09-25T20:20:39.744+00:00`이다. `rb_cue_count`는 객체 수다.
  - `contentCue` 행이 없던 곡은 `ID`를 곡 UUID로 해서 행을 새로 만든다.
- `djmdContent.CueUpdated`(글자형)에 지운 수 + 넣은 수를 더한다. NULL이면 0부터 센다.

### 자동 큐 (#145)

자동 큐는 rekordbox가 분석 때 넣는 메모리 큐다. 칸 값은 아래와 같다.

| 칸 | 값 |
|---|---|
| `Kind` | 0 |
| `Comment` | `CUE(Auto)` 또는 `1.1Bars` |
| `Color` | 255 |
| `ColorTableIndex` | 0 |
| `ActiveLoop`, `BeatLoopSize`, `CueMicrosec` | 0 |

- rekordbox 화면에서 자동 큐는 한도(10개)에 드는 메모리 큐로 보인다.
- `Color` 255는 이름 없는 일반 큐에도 많으므로 DJCrate는 **이름으로만** 자동 큐를 가린다.
- 덱 큐 목록에서 자동 큐는 '자동' 표시를 붙인 메모리 큐로 보인다.
- 일반 메모리 큐처럼 옮기기와 지우기를 할 수 있다. 이름, 루프, 종류도 고칠 수 있다.
- 지우기 말고 한 번이라도 고치면 자동 큐는 일반 큐가 된다. 이때 자동 이름은 빈 이름이나 사용자가 넣은 이름으로 바뀐다.
- 쓰기에 자동 큐 전용 규칙은 없다.
  - 건드리지 않은 자동 큐의 행과 JSON 객체는 바이트 그대로 둔다.
  - 자동 큐를 지우면 그 행을 지운다.
  - 고친 자동 큐는 같은 칸 값을 가진 직접 찍은 큐를 옮길 때와 같은 규칙으로 새로 넣는다.
  - `Comment`는 NULL이나 넣은 이름이다.
  - 색을 지정하지 않은 큐로 보아 `Color`는 −1, `ColorTableIndex`는 NULL이다.
- 골든 테스트 `RekordboxWriterGoldenTests`의 자동 큐 묶음이 이 모양을 칸 단위로 고정한다.
- **[미확인]** rekordbox에서 자동 큐를 옮겼을 때도 같은 모양인지는 실험하지 않았다.
- 아래 두 초안은 불러올 때와 쓸 때 곡의 자동 큐를 `base`·`cues`에 채운다(`CueDraft.includingAutoCues`).
  - #145 이전 초안. 이 초안의 `base`는 자동 큐를 빼고 만들었다.
  - 중복 합치기 초안
- 이 채우기는 변경으로 치지 않으므로 예전처럼 그 행은 그대로 남는다. 한도는 자동 큐까지 센다.

### 루프 (2026-09-26, Flip Flop·ときめき分類学 실험 + 기존 루프 105개)

- `OutMsec`은 끝 ms, `OutFrame`은 끝 ms × 150 / 1000을 내림한 값이다.
- 그 밖의 칸 값은 아래와 같다.

  | 칸 | 값 |
  |---|---|
  | `Color` | 255 |
  | `ColorTableIndex` | 0 |
  | `ActiveLoop` | 0/1. 활성 루프는 곡을 불러오면 자동으로 반복한다 |
  | `CueMicrosec` | 0 |
  | `Comment` | `''`. JSON에는 안 적는다 |

- `BeatLoopSize`는 분자 << 16 | 분모로 만든다. 값의 예는 아래와 같다.

  | 루프 | `BeatLoopSize` |
  |---|---|
  | 8박 | 524289 |
  | 16박 | 1048577 |
  | ½박 | 65538 |
  | 박에 맞지 않는 루프 | 0 |

- 새로 만든 루프는 JSON에도 `ActiveLoop`·`BeatLoopSize`가 있다. 옛 루프 JSON에는 이 칸이 빠진 경우가 있다.
- 활성 루프는 곡당 하나다. 라이브러리에 둘 이상인 곡은 없었다.
- rekordbox는 `CueUpdated`를 올리지 않은 채 활성 켜기를 행 제자리 UPDATE로 한다.
- DJCrate는 행을 지운 뒤 새로 넣는다. 결과 상태는 같다.

### 파일 형식별 탐색 위치

**MP3 CBR·M4A·WAV**: `InMpegFrame`과 `InMpegAbs`는 0, SeekInfo는 NULL이다.

**FLAC**

- `InPointSeekInfo`는 `"<큐 샘플이 든 FLAC 프레임 시작 샘플>,<그 프레임 바이트 위치 − 첫 오디오 프레임 위치>,<블록 크기>"`다.
- 루프가 아니면 `OutPointSeekInfo`는 `"0,0,0"`이다. 루프면 끝 지점을 같은 식으로 적는다.
- 이 식은 기존 큐 1,818개와 루프 끝 전부에 일치했다.
- 본문이 잘려 CRC-16이 맞지 않는 프레임이 있어도 프레임 머리의 번호를 따른다.
  - 근거는 손상 뒤 큐도 든 2026-10-03 #14 곡 D의 원래 곡 큐 13개다.
  - PVB2는 이때 규칙이 달라진다(아래 "곡 추가").

**VBR MP3**

- VBR MP3는 파일 머리가 Xing·VBRI인 파일이다. 프레임 길이가 들쭉날쭉한 파일도 VBR MP3로 본다.
- `InMpegFrame`은 1/75초 단위의 InFrame / 2다.
- `InMpegAbs`는 rekordbox가 세는 프레임 중 한 프레임의 바이트 위치다.
  - 고르는 프레임은 `floor(올림(InMpegFrame × 1000 / 75)ms × 샘플레이트 / 1000 / 1152) − 8`번째다. 음수면 0번째다.
  - 바이트 위치는 첫 센 프레임 기준이다.
  - LAME·`L3.99r1` 정보 프레임은 센다. 다른 인코더의 정보 프레임은 뺀다.
- 루프 끝도 같은 식이다. 루프가 아니면 끝은 0·0이다. SeekInfo는 NULL이다.
- ms를 버림하면 1,099개, 올림하면 1,118개 전부 맞는다. 대상은 기존 VBR 큐 1,118개와 루프 끝 6개다(`djc lab seekinfo-check`).
- 사본에서 VBR 200곡의 큐 886개를 지운 뒤 다시 쓰자 885개가 칸까지 같았다(`djc lab vbr-cue-repro`). 나머지 1개는 rekordbox가 옛날에 MPEG 칸을 비워 둔 큐다.
- `L3.99r1` 정보 프레임을 빼고 세던 때는 그 인코더 곡의 큐 1개가 한 프레임(313바이트) 어긋났다.
- 2026-10-03 같은 곡의 복제본에 rekordbox 7.2.18로 새로 찍은 큐도 같은 값이었다. 그래서 어긋남은 옛 상태가 아니라 세는 규칙의 차이였다.
- 정보 프레임을 세도록 고친 뒤 `seekinfo-check`의 VBR 큐 어긋남은 0이다(#14).

## 비트그리드 (ANLZ)

- `.DAT`의 `PQTZ`는 박마다 `박 번호(u16 1~4) · BPM×100(u16) · 시각 ms(u32)`를 담는다.
  - 시각은 정밀 시각을 **내림**한 값이다. 곡 앞 −1ms 안의 박은 0이다.
- `.EXT`의 `PQT2`는 머리와 본문으로 되어 있다.
  - 머리에는 첫 박, 마지막 박, 박 수, 정체 모를 u32가 있다.
  - 본문은 박마다 ms 아래 소수 × 1024 값을 담는다.
- rekordbox에서 그리드를 손으로 고치면 rekordbox가 PQT2를 머리 0, 본문 없음인 빈 형태로 바꾼다. DJCrate도 그렇게 쓴다.
- 그리드를 이동만 하면 DB는 안 바뀐다. `contentFile` 해시도 그대로다.
- 전체를 단일 템포로 바꾸면 아래 칸이 바뀐다.
  - `.DAT`의 `contentFile` 행: `Hash`(새 파일 MD5), `Size`, `rb_data_status`, `rb_local_usn`, `updated_at`
  - `djmdContent`: `BPM`(×100), `AnalysisUpdated`+1, `TrackInfoUpdated`+1, 상태, usn. 두 카운터는 글자형이다.
  - 소수(PQT2)가 없으면 첫 박을 ms + 0.5로 보고 다시 계산해 바이트까지 재현한다.
- `AnlzFile`은 태그 단위로 읽어 PMAI 전체 길이만 다시 적으므로 다른 태그는 바이트 그대로다.
- **파형 파일(.EXT)이 없는 곡은 rekordbox 분석 전 곡이다.** 이런 곡은 BPM 0, PQTZ 0박이다.
  - 그리드만 쓰면 파형 없는 채로 남으므로 막는다(2026-09-26 サラマンダー).
  - 분석 파일이 아예 없는 곡은 분석 붙이기로 쓴다(아래 "분석 붙이기").
  - `.DAT`만 있는 반쪽 곡은 막는다. 안내 문구는 "rekordbox에서 트랙 분석을 다시 한 뒤 쓰세요"다.

### 여러 템포 구간의 BPM 편집 (#11, 2026-09-28)

**[확인] rekordbox 7.2.18의 두 입력 경로는 다르다.**

실험 곡은 합성 WAV 두 곡이다.

- A: 「DJC 다구간 BPM 실험 A 첫 구간」
- B: 「DJC 다구간 BPM 실험 B 중간 구간」

사용자가 직접 편집한 뒤 종료했다. 종료 후 DB 스냅샷과 분석 파일의 실제 사본을 보존했다.

**평소 GRID BPM 칸에 입력할 때**

- 전체를 단일 템포로 바꾼다. A의 120→150→100을 121로 바꾸면 121 BPM 99박이 된다.
- 파일 행, 분석 카운터, 곡 정보 카운터는 기존 단일 템포 규칙대로 바뀐다.

**「현재 위치로부터 조정」 버튼의 별도 BPM 입력창으로 구간을 편집할 때**

- `PQTZ`를 바꾼다. `PQT2`는 빈 형태로 둔다. 다른 분석 태그와 `.2EX`·`.3EX`는 그대로다.
- B의 120→151→100을 별도 입력창으로 121→152→101로 바꾼 뒤 종료한 결과는 아래와 같다.
  - `djmdContent.BPM`은 12000→12100, `TrackInfoUpdated`는 '4'→'5'가 됐다.
  - 그 밖에는 `rb_local_usn`·`updated_at`만 바뀌었다.
  - **`AnalysisUpdated` '7'은 그대로**다.
  - **`contentFile`의 모든 칸이 그대로**다. 해시, 크기, 번호도 그대로다.
- 그래서 파일 행 해시가 실제 `.DAT`와 다를 수 있다. DJCrate는 이 해시를 임의로 새 해시로 맞추지 않는다.

**대표 BPM과 구간 경계**

- 첫 구간의 BPM이 그대로인 부분 편집은 대표 BPM을 바꾸지 않는다.
- DJCrate도 다구간 초안의 첫 BPM이 달라졌을 때만 대표 BPM과 곡 정보 카운터를 갱신한다.
- 단일 구간으로 합치는 초안은 전체 BPM 편집 경로를 쓴다.
- 구간 경계는 이전 구간에서 가장 가까운 박을 대체한다.
  - 예: B의 151 BPM 구간을 29.305초에서 끝내면 29.209초 박을 따로 넣지 않아 총 97박이다.
- 각 구간 시작은 정밀 소수가 없으면 ms + 0.5로 계산한다.
  - 121→152→101의 구간 시작 0.494·16.362·28.994초로 만들자 98박의 번호, BPM, 시각이 모두 일치했다.
- 고치지 않은 구간은 경계 직전의 원래 박까지 보존한다.
- ms 간격에서 역산한 BPM으로 다시 만들면 일부 박이 1ms 바뀔 수 있다.
- 경계를 늦춰 새로 늘인 박에는 위의 반 박 대체 규칙을 적용한다.
- 전체 이동과 박 번호 변경도 기존 박의 시각을 보존한다.

**안전 차단**

- 음원 안에서 시작하는 구간의 박이 경계 대체로 모두 사라지면 쓰지 않는다.
- 첫 구간이 없어지면 대표 BPM과 실제 첫 박의 BPM이 달라질 수 있다.
- 새 곡 분석과 기존 곡 쓰기에 같은 검사를 한다.

**사본 재현**

- `GridTempoExperimentRepro`는 A 전체 변경과 B 다구간 변경을 각각 실험 전 사본에 `RekordboxWriter.write`로 쓴다. 비교 대상은 아래 둘이다.
  - 분석 파일 `.DAT`, `.EXT`, `.2EX`, `.3EX`의 전체 바이트
  - 곡, 파일, 큐, 게인 표의 모든 대상 칸

## 오토게인 (`djmdMixerParam`)

- `GainHigh`·`GainLow`는 선형 게인 float32의 상위·하위 16비트다. `PeakHigh`·`PeakLow`는 샘플 피크다.

**저장 방식**

- 정보 패널은 **칸마다 따로 저장**한다. 한 줄 칸은 Enter로, 코멘트는 다른 칸으로 옮길 때 저장한다.
- 한꺼번에 저장하는 버튼은 없다. 정보 패널에는 앨범 아티스트 칸이 있다.
- 저장은 `djmdContent` 행을 제자리에서 UPDATE한다.
- `TrackInfoUpdated`(글자)는 **저장 한 번에 +1**이다. 관찰한 값은 아래와 같다.
  - 제목과 코멘트 저장: '1'→'3'
  - 장르, 작곡가, 연도, 트랙 번호 저장: '1'→'5'
  - 그 넷을 비움: '5'→'9'
- 값이 같아도 저장하면 +1이다(#173 S2 X4).
- 음원 파일 태그는 다시 쓴다. 그래도 `FileSize`와 다른 칸은 그대로였다.

**글자·숫자 칸**

| 칸 | 곡 행 칸 | 비우면 |
|---|---|---|
| 제목 | `Title` | — |
| 코멘트 | `Commnt` | `''` |
| 연도 | `ReleaseYear` | 정수 칸. 빈칸은 받지 않아 0을 넣으면 0 |
| 트랙 번호 | `TrackNo` | 정수 칸. 빈칸은 받지 않아 0을 넣으면 0 |

- 연도를 넣어도 `ReleaseDate`는 그대로였다. 실험 3의 발매일 있는 합성 곡에서도 연도 2012→2024→0은 발매일을 바꾸지 않았다.

**이름 칸**

| 곡 행 칸 | 이름 표 |
|---|---|
| `ArtistID`, `ComposerID` | `djmdArtist` |
| `GenreID` | `djmdGenre` |
| `AlbumID` | `djmdAlbum` |

- 있는 이름이면 그 행을 쓴다. 없으면 곡 넣기와 같은 모양의 새 행을 만든다.
- 새 이름 행의 칸은 아래와 같다.
  - ID: 32비트 난수
  - UUID: 소문자
  - `SearchStr`: NULL
  - 상태 칸: 0
  - `usn`: NULL
- 아티스트·장르 새 행은 `created_at` = `updated_at`이다.
- 새 앨범 행은 두 시각이 1~6ms 다르다. 근거는 #173 S1 T04, S3 V02, S4 A1, B2, C, D, F다. 상태 0 실험도 같았다.
- DJCrate는 두 시각에 같은 값을 쓴다. 재현에서 시각은 비교하지 않는다.
- 이름은 대소문자까지 정확히 찾는다. 대소문자만 다른 행만 있으면 새 행을 만든다 [확인].
- 근거는 #173 S1 T03, S2 U13, S3 V05다. 이 규칙은 DJCrate의 `Name = ?`와 같다.
- 비우면 아티스트·작곡가·앨범은 `''`, 장르는 `'0'`이다.
- 앨범을 비우면 앨범 아티스트도 함께 빈칸이 된다. 이때도 저장은 한 번이다.

**옛 이름 행 버리기**

- 아무 곡도 안 쓰게 된 옛 이름 행은 버린다.
  - 상태 0 행은 삭제 표시가 아니라 **실제로 지운다**.
  - 예: 아티스트 A→B로 바꾼 A, 비운 장르·작곡가, 비운 앨범이 그랬다.
  - 동기화 행인 256 행과 257 앨범 행은 258과 삭제 표시로 바꾼다. 자세한 규칙은 아래 "동기화 상태(256·257)인 곡"에 있다.
  - 지운 앨범의 앨범 아티스트 행은 아무 곡도 안 쓰는데도 남았다.
  - 다른 곡도 쓰는 이름은 그대로다.
- 동기화(256·257) 행을 버릴지 정할 때는 표와 상관없이 **살아 있는 곡의 참조만** 센다 [확인]. 근거는 아래 표와 같다.

  | 표 | 근거 | 관찰 |
  |---|---|---|
  | 앨범 | #173 S2 U04 | 지운 곡 여럿이 가리키던 동기화 앨범도 비우자 258. U01·U14도 동기화 앨범 |
  | 아티스트 | S4 E1 | 지운 곡 하나가 `ArtistID`로 가리키던 동기화 아티스트도 258 |

- 지운 곡 행은 그대로 남아 258 행을 계속 가리킨다.
- 지운(258·262) 앨범의 앨범 아티스트 칸이 동기화 아티스트를 붙잡는지는 보지 못했다 [미확인].
- DJCrate는 쓰지 않는 쪽을 골랐다(결정). 아티스트의 앨범 아티스트 참조는 지운 앨범까지 세어 행을 남긴다.

- S1~S4 기준점과 결과 모두를 조사한 결과는 아래와 같다.
  - 살아 있는 참조가 0인 살아 있는 이름 행은 없었다.
  - 지운 곡만 가리키는 상태 0 이름·앨범 행도 없었다.

**앨범 행**

- **아티스트를 고치면 rekordbox는 그 곡의 앨범 행도 저장한다.**
  - `AlbumArtistID`가 NULL이면 `''`가 된다. 값이 있으면 그대로다.
  - 앨범 행은 변경 번호와 `updated_at`을 받는다. 근거는 묶음 2의 실험곡 5다.
  - 있는 앨범 이름에 곡을 붙일 때도 rekordbox는 그 앨범 행을 같은 식으로 저장했다.
  - 제목·코멘트·장르를 고칠 때는 앨범 행이 그대로였다. 작곡가·연도·트랙 번호도 같았다.
  - 저장하는 앨범 행은 자기 상태를 따라 256 → 257이 된다. 0·257은 그대로다(#173).
- 앨범 이름이 유일하면 앨범 아티스트를 **제자리에서** 고친다. 새 이름이면 아티스트 행을 더한다.
- 앨범 아티스트의 빈 값은 `''`이다.
- 더 이상 참조하지 않는 이전 아티스트 행은 버린다. 다른 곡이나 앨범이 참조하면 남긴다.
- 지운 곡만 함께 쓰던 앨범도 "유일한 곡의 앨범"이다(#173 S2 U01·U14).
- 공유 앨범도 같은 행을 고치므로 **선택하지 않은 곡의 앨범 아티스트까지 바뀐다**.

- 새 앨범 행의 칸은 아래와 같다.
  - `AlbumArtistID`는 기존 앨범 아티스트 ID를 이어받는다. 없으면 NULL이 아니라 `''`다.
  - `Compilation`은 0, `ImagePath`·`SearchStr`는 NULL이다.
  - 나머지 이름 행 공통 칸은 위와 같다.
- 이전 앨범은 아무도 참조하지 않으면 버린다.
- 이름이 유일한 기존 앨범에 붙이면 그 앨범 행을 저장한다. 이때 앨범 아티스트를 곡의 이전 앨범 아티스트로 덮어쓴다.
- 다른 앨범 아티스트를 가진 앨범에 붙이면 다른 곡까지 바뀌므로 DJCrate에서는 막는다.

태그는 `RekordboxWriter+Tags`가 반영(⌘⇧E) 때 쓴다(#1).

**쓰는 범위**

- rekordbox 라이브러리만 쓴다. 음원 파일 태그는 건드리지 않는다(2026-09-26 결정). 확인 창에 "음원 파일의 태그는 그대로"라고 알린다.
- 여러 칸을 한 번에 쓰되, 결과는 **칸마다 한 번 저장한 것과 같다**.
  - `TrackInfoUpdated`에 바꾼 칸 수를 더한다.
  - 앨범을 비울 때 앨범 아티스트도 비우면 하나로 센다.
  - 동명 앨범이라 새 앨범으로 옮겨도 아티스트 칸 하나로 센다.
  - 비운 값은 위와 같다.

**버릴 행과 참조 세기**

- 버릴 이름·앨범 행은 상태 0이면 지운다. 256 행과 257 앨범은 258로 표시한다.
- 참조로 세는 칸은 아래와 같다.
  - 곡 행: 아티스트, 작곡가, 원곡 아티스트, 리믹서, 앨범, 장르
  - 앨범: 앨범 아티스트
- 세는 범위는 버릴 행의 상태로 정한다(`ReferenceRows.scope`).

  | 버릴 행 | 세는 범위 |
  |---|---|
  | 동기화(256·257) 행 | 표와 상관없이 살아 있는 곡 + 모든 앨범(`liveSongs`) |
  | 상태 0 행 | 지운 곡·앨범까지 모두(`all`) |

- `liveSongs`에서 아티스트의 앨범 아티스트 참조는 지운 앨범까지 센다. 258로 표시한 앨범도 앨범 아티스트 칸을 그대로 가리킨다.
- 지운 곡만 가리키는 동기화 아티스트·장르도 258이다(S4 E1·E2).
- 지운 앨범의 앨범 아티스트 칸만 남은 동기화 아티스트는 [미확인]이라 쓰지 않는 쪽으로 남긴다.
- 개수는 칸마다 인덱스로 센 뒤 UNION ALL로 잇는다(`ReferenceCount`). 곡 개수(살아 있음·지움별)와 앨범 개수만 센다.
- 칸 목록은 곡 빼기와 같다(`RekordboxTrackWriter.contentReferenceColumns`).
- 곡 빼기(`RekordboxTrackWriter.referenceCount`)는 지운 곡까지 세는 옛 규칙 그대로다.

**앨범 저장과 동명 앨범**

- 아티스트를 고치면 곡의 앨범 행을 저장한다(256 → 257). 비우기도 같다.
- 곡의 앨범 이름을 살아 있는 앨범 둘 이상이 쓰면 앨범 행을 저장하지 않는다. 대신 같은 이름의 새 앨범으로 곡을 옮긴다(위 "동명 앨범").
- 곡의 앨범이 몇째로 만든 행이든 같다. 옮길지는 트랜잭션 안에서 앞 초안을 쓴 DB로 센다.
- 앞 초안이 같은 이름 앨범 하나를 버려 그 이름이 하나뿐이 될 수 있다. 그러면 뒤 초안은 옮기지 않은 채 제자리에서 저장한다. 하나씩 저장한 결과와 같다.

**변경 번호**

변경 번호는 정보 패널 칸 순서를 따르되 앨범을 아티스트보다 앞에 둔다.

1. 앨범
2. 아티스트. 그 뒤 바뀐 앨범 행
3. 장르
4. 작곡가 새 행
5. 곡 행
6. 버린 행(258)
7. 곡 행 한 번 더(258을 썼을 때)

앨범과 아티스트를 함께 고치면 rekordbox에서 앨범 → 아티스트 순으로 저장한 결과와 같다. 이 곡만 쓰던 옛 앨범을 저장했다가 다시 버리는 일은 없다.

**곡 상태**

- 곡 상태 0·256·257이면 위 칸을 모두 쓴다. 동기화 곡은 곡 행 상태를 256 → 257로 올린다.
- 자세한 규칙은 아래 "동기화 상태(256·257)인 곡"에 있다.
- 아래 경우는 막는다.
  - 곡 상태가 그 밖의 값이다.
  - 저장할 앨범의 상태가 0·256·257이 아니다. NULL도 막는다.

**재생 목록 XML 쓰기**

- 곡 정보를 쓴 곡이 든 살아 있는 재생 목록마다 `masterPlaylists6.xml`의 Timestamp를 쓴 시각 한 값으로 고친다.
  - 곡 정보는 아홉 칸과 키·평점·곡 색이다.
  - 지운 목록과 지운 곡 항목은 뺀다.
- 그 곡이 든 살아 있는 목록이 없는 초안은 XML을 읽지도 고치지도 않는다.
- 어느 칸이 XML을 고치는지는 `RekordboxWriter.playlistXMLTagKeys` 한 곳에서 정한다.
- 쓰는 DB 옆 파일만 고친다. 그 파일이 없으면 DB만 쓴다.
- 아래 경우에는 그 곡정보 초안들만 할 일과 함께 막는다.
  - 사본 옆 XML이 라이브 XML의 링크다.
  - XML이 필요한데 읽지 못한다.
- 막힘 결과의 곡 이름은 다른 막힘처럼 DB `Title`이다. 같은 쓰기의 큐·그리드·게인 초안과 다른 초안은 쓴다.
- 재생 목록·합치기 쓰기는 다르다. XML이 링크일 때와 읽지 못할 때는 예전처럼 백업 전에 쓰기째 막는다(`adjacentFileIsLive`·`checkAdjacentFile`).
- XML은 재생 목록 쓰기와 같은 경로로 DB를 확인한 뒤, 고칠 목록의 Timestamp를 모아 한 번에 적는다.
- XML을 적지 못하면 DB와 XML 모두 백업으로 되돌린다.
- 곡이 든 목록의 NODE가 없는 경우처럼 고칠 줄이 없으면 XML을 다시 쓰지 않는다.
- XML 쓰기나 다시 읽기가 실패하면 DB를 되돌리기 전에 원본 XML부터 다시 쓴다(`writePlaylistXML`). 재생 목록 쓰기 #38과 같은 순서다.
- 그 밖의 되돌리기에서 XML은 DB를 되살린 뒤에만 되살린다(`restoreFiles`). 사용자의 "쓰기 전으로 복원…"도 같다.
- XML은 원자적으로 쓰므로 반쯤 쓰인 상태가 없다. 그래서 DB 복원이 실패하면 재생 목록 구조가 DB와 어긋나지 않게 XML도 지금 상태로 둔다.

**base와 값 확인**

- 공유 앨범 아티스트 변경과 동명 앨범으로 붙이기도 막는다. 막힌 이유와 rekordbox에서 할 일을 알린다.

**버릴 행 정하기**

버릴 행은 미리 계산하지 않는다. 아래 순서로 정한다(`releaseNames`).

1. 초안마다 SAVEPOINT를 건다.
2. 곡 행·앨범 행·새 이름 행을 실제로 쓴다.
3. 후보마다 실제 참조 수를 센다.
4. 참조가 남으면 그대로 둔다.
5. 상태 0이면 지운다. 256·257 앨범이면 258로 표시한다.

- 버릴 행이 아래와 같으면 그 초안만 변경 번호까지 SAVEPOINT로 되돌린다.
  - 257 아티스트·장르
  - 상태가 0·256·257이 아닌 행
- 되돌린 초안은 막힘으로 보고한다. 같은 쓰기의 나머지는 쓴다.
- 미리 계산하던 때는 #173 3차 리뷰에서 찾은 문제가 있었다(`RekordboxTagReleaseTests`).
  - 앨범 아티스트와 아티스트를 같은 새 이름으로 바꾸면 계산이 실제와 어긋났다.
  - 그래서 큐와 그리드까지 쓰기 전체가 되돌아갔다.

**백업 전 확인** (`checkTagDrafts`)

- 백업 전 확인은 DB를 바꾸지 않은 채 분명히 알 수 있는 막힘만 본다.

    - 공유 앨범의 앨범 아티스트
    - 다른 앨범 아티스트의 앨범

  - 그 앨범의 상태

  - 앨범 아티스트가 같은지

  - 합치기

### 키 (#5, `RekordboxWriter+Key`, 2026-10-04)

- 큐·그리드·게인과 재생 목록의 공통 규칙과 같다. 공통 규칙은 256 → 257이고 이미 257이면 그대로다.
- **변경 번호**: 다시 저장 한 번에 `localUpdateCount`가 +2였다. 곡 행은 마지막 번호를 받았다.
- 첫 구간은 같은 세션의 상태 0 곡 코멘트 저장과 섞여 +3이었으므로 저장별로 나눌 수 없다.
- DJCrate는 행마다 번호 하나를 쓴다. 번호 값은 비교하지 않는다.
- 같은 세션에서 저장한 상태 0 곡의 코멘트는 곡 행의 `Commnt`·`TrackInfoUpdated` +1과 번호·시각만 바뀌었다. 위 상태 0 규칙과 같다.

**DJCrate가 쓰는 것**

초안:

- 초안은 곡마다 동작과 base를 담은 `ArtworkDraft` 하나다.
  - 동작은 넣기·바꾸기(그림 바이트)나 지우기다.
  - base는 곡 행 `ImagePath`와 살아 있는 그림 파일 행의 경로, Hash, Size, 상태다.
- 바꾸기는 곡 행이 안 바뀌므로 rekordbox에서 바꾼 그림은 파일 행으로 알아챈다.
- 고른 그림의 사본은 원본 파일을 옮겨도 남도록 DJCrate 초안 폴더에 둔다(`artwork-drafts/<UUID>.<SHA-256>.image`). 해시는 초안에 둔다.
- 저장 순서는 새 사본 → 초안 → 옛 사본 지우기다. 그래서 뒤에서 도는 손상 검사가 언제 보아도 초안이 가리키는 사본이 있다.
- 초안이 가리키지 않는 사본은 손상으로 보지 않은 채, 그 곡의 초안을 저장할 때나 버릴 때 지운다.

쓰기:

- 쓰기는 `RekordboxWriter.write(artworks:)`의 같은 트랜잭션에서 BPM 그리드 다음, 태그 앞에 초안마다 SAVEPOINT로 한다.
- 같은 곡의 태그가 곡 행에 마지막 번호를 준다.
- 넣기·지우기는 같은 곡의 큐·BPM 검증이 볼 곡 행 번호를 맞춘다. 칸과 순서는 위 표 그대로다.
- INSERT 행은 #4와 같은 `RekordboxTrackWriter.fileRow`로 만든다.
- 되살리기·바꾸기·258은 다시 읽어, 바꾸는 칸 말고는 고치기 전 행 그대로인지까지 본다.

파일:

- 그림 셋은 `TrackArtwork.make`로 만들어 커밋과 다시 읽기 뒤에 쓴다.
- 바꿀 옛 세 파일과 지울 옛 세 파일은 쓰기 백업의 `anlz/`에 `artwork-<n>.jpg`로 둔다. manifest에는 share 기준 경로를 적는다.
- 넣은 파일은 `createdFiles`에 적는다.
- 파일을 쓰다 실패하면 아래 순서로 되돌린다.
  1. 만든 파일을 지운다.
  2. 옛 파일을 원래 바이트로 되돌린다.
  3. DB를 되돌린다.
- "쓰기 전으로 복원…"도 같은 백업으로 옛 그림과 행을 되살린다. 넣은 파일은 지운다.
- 쓴 뒤 `artwork.jpg`의 MD5와 크기가 파일 행과 같은지 본다.
- 쓴 초안과 사본은 백업 `artwork-drafts/`에 두어 되돌리면 다시 살린다.
- 파일은 곡 빼기와 같은 경계 `ownedCandidates`로 곡 UUID 폴더의 세 이름만 다룬다.
- 이 경계는 심볼릭 링크·음원 경로·다른 곡이 쓰는 폴더를 거부한다. 지우기는 폴더를 남긴다.

## 시간축

- rekordbox는 압축 음원 앞 지연을 잘라 내지 않으므로 rekordbox 시각 = AVFoundation 시각 + 인코더 지연이다.
- 인코더 지연은 아래와 같다.

  | 형식 | 지연 |
  |---|---|
  | AAC | 2112샘플 |
  | LAME MP3 | +51.2ms(576+529+1152) |
  | ffmpeg MP3 | 프라이밍+529 |
  | 태그 없는 MP3 | 529샘플 |
  | 무손실 | 0 |

- 계산은 `RekordboxTimeline.predictedOffset(url:)`이 한다. 덱·초안의 모든 시각은 rekordbox 시간축이다.

## 쓰기 절차 (`RekordboxWriter.write`)

1. rekordbox나 rekordboxAgent가 실행 중이면 거부한다. `-wal`이 남아 있어도 거부한다.
2. 백업을 뜬다. master.db(+wal/shm) 전체와 바꿀 분석 파일을 `rekordbox-backups/<시각>-write/`에 복사한다. 복사 중 원본이 바뀌면 실패한다.
3. `BEGIN IMMEDIATE` 한 트랜잭션에서 쓴다.
4. 같은 연결로 다시 읽어 초안과 칸마다 비교한다.
   - 비교 기준은 큐 목록 `expectedCues(after:)`다. 이 목록은 초안의 변경(`CueDraft.changes`)만 base에 반영한 것이다.
   - 1ms 미만 차이는 변경이 아니다.
   - 그리드 따라가기로 1ms 미만 움직인 큐는 rekordbox 값 그대로 둔다(#73).
5. 커밋 뒤 다시 열어 한 번 더 검증한다. `PRAGMA quick_check`와 `cipher_integrity_check`도 한다.
   - 커밋한 쓰기는 종류와 상관없이 모두 이 검증을 거친다(#135).
   - BPM만 바꾼 그리드도 곡 BPM·카운터·파일 행을 다시 읽는다.
   - 게인만 쓴 경우도 오토게인 칸을 다시 읽는다.
6. 그 뒤 분석 파일과 `masterPlaylists6.xml`을 쓴다. 백업에 원본을 함께 둔다.
7. 어느 단계든 실패하면 백업으로 되돌린다.

초안을 만든 뒤 rekordbox에서 그 곡이 바뀌었으면(base 불일치) 그 곡은 쓰지 않는다.

## 곡 추가·삭제 (`RekordboxTrackWriter`, 2026-09-26 묶음 1·2 실험)

**추가(분석 전)**

rekordbox가 자동 분석을 끈 채 파일을 넣으면 78칸짜리 `djmdContent` 행 하나만 생긴다. `RekordboxTrackWriter.contentRow`는 형식까지 이 행을 따른다.

- 곡 ID는 1~2^28 난수다. 라이브러리 14,155행이 전부 이 범위였다.
- 아티스트·앨범·장르 ID는 32비트 난수, UUID는 소문자 v4다.
- 태그(ID3·iTunes·Vorbis)에서 아래 값을 읽는다.

  | 구분 | 값 |
  |---|---|
  | 곡 행 칸 | 제목, 코멘트, 연도, 트랙, 디스크, ISRC |
  | 이름 행 | 아티스트, 앨범, 앨범 아티스트, 장르, 작곡가(`djmdArtist`) |

- 제목이 없으면 확장자를 뺀 파일 이름을 쓴다. 설명이 붙은 ID3 코멘트(iTunNORM 등)는 쓰지 않는다.
- 이름이 없으면 새 행을 만든다.
- 그 밖의 칸 값은 아래와 같다.

  | 칸 | 값 |
  |---|---|
  | 분석 칸 | 0·빈 값 |
  | `Analysed` | 0 |
  | `ContentLink` | 14 |
  | `AnalysisUpdated`, `TrackInfoUpdated`, `CueUpdated` | NULL |
  | 길이 | 초 반올림 |
  | `rb_file_id` | 음원 파일 inode |
  | `DateCreated` | 파일 만든 날 |
  | `StockDate` | 넣은 날 |
  | `MasterDBID`, `DeviceID` | 라이브러리 공통값 |

- 경로와 파일 이름은 NFC다.
- 변경 번호는 관련 행(아티스트·앨범·장르)이 먼저 받는다. 곡 행이 마지막이다.

**추가(분석 포함)**

위 행에 분석 칸을 채운다. 분석 파일, 파일 행, 오토게인 행도 더한다.

| 칸 | 값 |
|---|---|
| 분석 경로 | `/PIONEER/USBANLZ/<UUID 앞 3자>/<나머지>/ANLZ0000.DAT` |
| `Analysed` | 105 |
| 길이 | 초 버림 |
| `AnalysisUpdated` | "1"(글자) |
| `TrackInfoUpdated` | "1"(글자). 두 카운터 모두 첫 BPM/Grid 분석만 만든다 |

비트레이트는 형식마다 다르다.

| 형식 | 비트레이트 |
|---|---|
| CBR MP3 | 프레임 비트레이트 |
| LAME VBR MP3 | 0 |
| AAC | esds 평균 비트레이트. 없으면 0. streamType 바이트 0x14도 있다 |
| WAV | 샘플레이트×비트×채널 |
| FLAC | 0 |

`.DAT` 태그는 아래 순서다.

| 태그 | 내용 |
|---|---|
| `PPTH` | `?/파일 이름` UTF-16BE + NULL |
| `PVBR` | 머리 0, 탐색표 400칸. 끝값은 MP3면 rekordbox가 세는 프레임 수×1152, AAC·WAV는 0 |
| `PQTZ` | — |
| `PWAV` | — |
| `PWV2` | — |
| `PCOB` | 핫, 빈 |
| `PCOB` | 메모리, 빈 |

- 같은 그리드로 다시 만들면 아래 태그가 바이트까지 같다: 머리, PPTH, PVBR, PQTZ, PCOB.
- `.EXT`·`.2EX`는 baken의 MIT 규칙을 옮긴 파형 생성기 `RekordboxWaveforms`가 만든다.
- 흑백 파형 높이는 99.5% 바이트 일치한다. 색·3밴드·미리 보기는 근사다.
- rekordbox 7.2.18은 우리 파일을 그대로 보였다. 확인한 곡은 "サラマンダー 복사본"이다.
- `contentFile` 행은 파일마다 하나다. 칸은 아래와 같다.
  - ID: `<곡 UUID>_<경로, /는 %2F>`
  - MD5, 크기
  - `rb_local_path`
  - `rb_priority`: 50
- 이 행이 없어도 표시는 된다. 그래도 rekordbox처럼 넣는다.
- 변경 번호 순서는 관련 행 → (아트워크 파일 행) → 오토게인 행 → 곡 행 → .2EX → .DAT → .EXT다.
- rekordbox는 곡 행을 먼저 넣은 뒤, 분석이 끝나면 곡 행을 다시 고쳐 새 번호를 받는다. 곡 행 뒤·.2EX 앞에는 .3EX 행도 넣는다.
- 근거는 2026-09-26 아트워크 실험 세션이다. 이 세션은 자동 분석을 켠 채 넣은 합성 WAV 3곡을 보았다. 분석 전 곡을 분석한 "DJC 실험 아트"도 보았다.
- DJCrate는 곡 행을 한 번만 넣으므로 rekordbox의 마지막 번호 순서를 따른다.
- 카운터는 분석 항목과 횟수에 따라 다르다. 조성·Phrase 없이 첫 BPM/Grid만 만드는 두 경로는 '1'·'1'이다(2026-09-27 #95).
- 자세한 내용은 아래 "분석 카운터"에 있다.
- `ContentLink`는 분석 구성 비트다.

  | 값 | 뜻 |
  |---|---|
  | `0x3C060E` | 보통(라이브러리 곡 대부분) |
  | `0x2C060E` | 보컬 분석 없음 |
  | +`0x10000` | 프레이즈 있음 |

- DJCrate가 만드는 분석에는 프레이즈·보컬이 없으므로 `0x2C060E`를 쓴다.
- DJCrate가 만들 수 없는 것은 셋이다.
  - `PSSI`(프레이즈)
  - `PVDI`(보컬)
  - `.3EX`. MessagePack `embedding`이며 rekordbox AI 특징값이다.
- rekordbox에서 Phrase만 분석하면 우리 태그는 바이트 그대로 둔 채 `PSSI`만 덧붙인다.
- USB에서는 로컬 태그를 마스크로 옮길 뿐 새로 만들지 않는다(`docs/usb-internals.md` §4).

**MP3 프레임 세기**

- 첫 프레임 안에 LAME 태그가 있는 LAME 정보 프레임은 소리로 센다.
- 다른 인코더(ffmpeg Lavc 등)의 정보 프레임은 세지 않는다.
- 인코더 칸이 `L3.99r1`인 정보 프레임도 LAME처럼 센다. 근거는 2026-10-03 #14 곡 F다.
  - 세면 큐 2개와 PVBR 400칸, 끝값, `PWV3` 길이가 맞는다.
  - 빼면 PVBR 400칸이 모두 다르다. 파형도 4칸 짧다.
- 이 인코더를 확인하지 않았으므로 시간축 보정(`predictedOffset`)에는 LAME 규칙을 붙이지 않았다.
- 다음 오디오 프레임에 "LAME3.99U"가 찍힌 ffmpeg 파일이 있어서, LAME은 첫 프레임 안에서만 찾는다.

**VBR MP3 탐색표**

- 칸 k는 센 프레임 중 `floor((k+1)·n/400) − 8`번째 프레임의 바이트 위치다. 위치는 첫 센 프레임 기준이다. 음수면 0번째다.
- 라이브러리의 LAME VBR 수백 곡에서 400칸이 전부 일치했다. CBR은 수천 곡 중 3곡을 뺀 모두가 0이다.
- 8프레임 앞은 디코더 비트 저장소 몫으로 보인다.

**FLAC**

- 비트레이트는 0이다. 비트는 STREAMINFO에서 읽는다.
- `PVBR`은 탐색표와 끝값 모두 0이다. 대신 `.EXT` 끝(`PWV4` 뒤)에 `PVB2`를 붙인다.

  | 부분 | 모양 |
  |---|---|
  | 머리 0x20 | `u32 0`, `u64 전체 샘플`, `u32 400`, `u32 20` |
  | 칸 400개 × 20바이트 | `u64 프레임 시작 샘플`, `u64 첫 프레임 기준 바이트 위치`, `u32 블록 크기` |

- 칸 k는 샘플 `k · floor(전체 샘플 / 400)`이 든 FLAC 프레임이다. 나눗셈을 먼저 버리므로 뒤 칸일수록 조금 앞을 가리킨다.
- 라이브러리 천여 곡 중 2곡을 뺀 모두가 바이트까지 일치했다(`djc lab pvb2-check`).
- 나머지 2곡은 2026-10-03 복제본 재분석으로 가렸다(#14).
  - **곡 E**(44.1kHz/16비트): 새 분석은 DJCrate 계산과 400칸이 같다. 원래 곡의 저장값만 다르다.
  - DB의 파일 크기도 지금 음원과 달라서, 분석 뒤 파일이 바뀐 것이다.
  - **곡 D**(96kHz/24비트): 새 분석이 원래 곡 저장값과 바이트까지 같다.
  - 곡 D는 가운데 프레임 하나가 14바이트 짧아 CRC-16이 맞지 않는다.
  - rekordbox는 PVB2에서 **그 프레임을 뺀 채 이어서 번호를 매긴다**.
  - 칸의 시작 샘플을 센 순서 × 블록 크기로 보면 400칸이 일치한다. 프레임 머리 번호를 따르면 374칸이 다르다.
  - 전체 샘플은 STREAMINFO 값 그대로다.
- 그런데 라이브러리의 다른 FLAC 1곡은 CRC-16이 맞지 않는 프레임이 12개다. 그런데도 저장 PVB2가 프레임 머리 번호 규칙과 같다(2026-10-03 `pvb2-check` 진단).
- 손상 모양에 따라 rekordbox 규칙이 갈린다. [추정] 곡 D는 프레임이 짧아 디코더가 다음 프레임 머리까지 먹어 한 프레임을 잃은 것으로 보인다.
- 어느 쪽인지 가릴 규칙은 확인하지 않았으므로, DJCrate는 CRC-16이 맞지 않는 프레임이 있으면 분석을 막는다.
- 그 1곡도 막힌다. 규칙은 #193 이슈에서 확인한다.
- 2026-10-03 실험 뒤 사본과 분석 파일 사본으로 다시 대조하면 어긋남은 곡 E 원래 곡 1곡이다.
- 막아서 비교에서 뺀 곡은 곡 D 원래 곡·복제본과 위 1곡이다.

**막는 형식**

- 16/24비트·44.1/48kHz·스테레오 밖의 미확인 ALAC 조건
- MPEG-1(32·44.1·48kHz)이 아닌 ffmpeg VBR. 이 VBR의 576샘플 프레임은 확인하지 않았다.
- L3.99r1을 포함한 그 밖의 비LAME VBR
- STREAMINFO 전체 샘플과 프레임 합이 다른, 프레임이 중간에 끊긴 MP3·FLAC
- 마지막을 뺀 프레임 중 CRC-16이 맞지 않는 프레임이 있는 FLAC. 마지막 프레임은 뒤에 붙은 태그와 끝을 가릴 수 없어 보지 않는다.

**키** (#5, 2026-10-04)

- `RekordboxTrackWriter.add`의 `keys`가 사용자가 고른 키(Camelot 이름)를 곡을 넣는 같은 쓰기에서 쓴다.
- 새 실험 없이, 확인한 두 동작을 그 순서대로 한 트랜잭션에 잇는다.
  1. rekordbox에서 곡을 넣는다. 위 두 경우 모두 곡 행은 `KeyID` `'0'`이다.
  2. 정보 패널에서 키를 저장한다. 근거는 위 "태그 (곡 정보)"의 "키"에 있다.
     - 묶음 2 S1: 분석 안 된 상태 0 곡 넣기
     - #173 S1 T13·S2 U10·S5 K1
- 순서는 곡 넣기 → 큐 → 키다. 곡 넣기 안의 순서는 관련 행 → 오토게인 → 곡 행 → 분석 파일 행이다.
- 키는 곡 행에서 키만 고친 태그 초안을 태그 쓰기(`applyTags`)로 쓴다. 기준은 방금 넣은 곡의 `currentTags`다.
- 태그를 마지막에 쓰는 기존 순서와 같아서 곡 행이 마지막 번호를 받는다.
- 분석 붙이기(`RekordboxWriter+Analysis`)는 `TrackInfoUpdated`가 NULL인 곡만 받으므로 분석은 늘 키보다 먼저다. 곡 넣기의 분석은 곡 행에 함께 들어간다.
- 곡 행의 값은 아래와 같다.

  | 칸 | 값 |
  |---|---|
  | `KeyID` | 고른 줄 ID(글자) |
  | `TrackInfoUpdated`, 분석 없이 넣음 | NULL → `'1'` |
  | `TrackInfoUpdated`, 분석까지 넣음 | 첫 BPM/Grid `'1'` → `'2'` |
  | 상태 | 0 그대로 |

- `djmdKey`와 다른 표는 그대로다.
- 넣는 곡은 같은 쓰기에서 어느 재생 목록에도 들어가지 않는다. 그래서 `masterPlaylists6.xml`도 그대로다.
- 목록 연결은 뒤의 재생 목록 초안에서 다룬다.
- 음원 파일의 키 태그는 쓰지 않는다(#5 결정).
- 아래 경우에는 **키만** 막는다. 이유는 따로 쓸 때와 같다(`resolveKeyID`).
  - 키 줄이 없다.
  - 살아 있는 줄이 둘 이상이다.
  - 삭제 표시 줄뿐이다.
  - Camelot이 아닌 이름이다.
- 키를 막을 때는 SAVEPOINT와 번호를 되돌린 뒤 곡을 키 없이 넣는다(`keyReason`).
- 따로 썼을 때도 넣기는 성공한다. 키 쓰기만 막히므로 결과 DB가 같다.
- 곡째 막으면 "한 번에 = 따로"가 깨지므로 그쪽은 고르지 않았다.
- 앱은 막힌 큐처럼, 고른 키가 사라지지 않게 그 키를 새 곡의 키 초안으로 옮긴다.
- 넣는 곡은 처음부터 `'0'`이므로 비운 키는 할 일이 없다.

검증과 되돌리기:

- 커밋 전후로 아래를 다시 읽는다.
  - 키를 쓴 뒤 모양의 곡 행 전체
  - 큐
  - `KeyID` 칸 자체까지 읽는 키(`verifyTags`)

- 넣기 끝에 백업에 추가 목록을 남기지 못하면 결과에 경고로 알린다.

**아트워크** (#4)

- rekordbox는 곡을 **분석할 때** 음원 내장 그림으로 파일 셋을 만든다. 음원 내장 그림은 ID3 APIC·iTunes covr·FLAC PICTURE다.
- 자동 분석을 끈 채 넣을 때는 만들지 않는다. XML로 들어온 곡(`Analysed` 41)에도 없었다.

실험은 2026-09-26 rekordbox 7.2.18에서 했다.

1. 1200×900 JPEG 앞표지(APIC)가 든 MP3 "DJC 실험 아트"를 자동 분석을 끈 채 넣었다. 아티스트·앨범은 라이브러리에 없던 이름이다.
2. rekordbox를 종료했다.
3. 다음 세션에서 자동 분석을 켜자 rekordbox가 이 곡을 분석했다.

넣기 전·넣은 직후·분석 뒤 스냅샷을 `djc lab db-diff`로 비교했다. 넣기 전 스냅샷은 rekordbox 자동 백업과 같은 상태다.

- **넣을 때**
  - `djmdArtist` → `djmdAlbum` → `djmdContent` 행만 생겼다. 변경 번호도 이 순서다(`localUpdateCount` +3).
  - `ImagePath`는 빈 값이다. 파일 행과 아트워크 파일은 없다.
  - `djmdAlbum.ImagePath`는 NULL, `imageFile` 표는 그대로(0행)다.
  - 곡 행은 `djc lab track-add-repro`로 19칸 모두 같았다.
- **분석할 때**: #87에서 넣은 직후 스냅샷과 분석 뒤 스냅샷을 곡 ID로 갈라 다시 정리했다.
  - 번호 순서는 아래와 같다.
    1. `artwork.jpg` 파일 행. 분석 결과를 쓰기 2초 전에 번호를 받았다.
    2. 오토게인 행
    3. 곡 행(`ImagePath`와 분석 칸)
    4. 파일 행 .3EX → .2EX → .DAT → .EXT
  - 아트워크 행과 오토게인 행 사이 빈 번호에는 다른 곡 한 행만 있다. 나머지 번호는 어느 표에도 없다.
  - 오토게인 행이 N, 곡 행이 N+2이고 N+1은 어느 표에도 없다. 같은 세션에서 자동 분석으로 넣은 합성 WAV 3곡도 같은 모양이다.
  - 그래서 곡 행이 번호를 두 번 받는 것으로 보인다. DJCrate는 한 번 준다.
  - `djmdAlbum.ImagePath`와 `imageFile`은 그대로다.
  - 곡 행에서 바뀐 칸은 아래와 같다.

    | 칸 | 값 |
    |---|---|
    | `BitRate`, `BitDepth`, `SampleRate` | 바뀜 |
    | `ImagePath`, `AnalysisDataPath` | 바뀜 |
    | `Analysed` | 0→105 |
    | `ContentLink` | 14→0x2C060E |
    | `AnalysisUpdated`·`TrackInfoUpdated` | NULL→'1'·'1' |
    | 변경 번호, `updated_at` | 바뀜 |

  - 동기화한 적 없는 곡이라 `rb_data_status`는 0 그대로다. `Length`(40)도 그대로다.
  - 이 합성 MP3에서는 박을 찾지 못해 BPM 0, `PQTZ` 0박이었다.
  - 그래도 `.EXT`·`.2EX`·`.3EX`까지 만들었다. 파일이 모두 있으므로 아래 "반쪽 분석"과 다르다.
- **이미 분석한 곡**에서는 그림을 다시 뽑지 않는다.
  - 아트워크를 넣기 전의 DJCrate로 분석까지 붙여 넣은 곡 중 음원에 그림이 있는 곡은 3곡이다.
  - 그 뒤 rekordbox를 켜도, 위 자동 분석 세션까지도 이 곡들의 `ImagePath`는 빈 값이었다.

폴더와 파일 셋:

- 폴더는 분석 폴더와 같은 규칙으로 곡 UUID로 정한다: `/PIONEER/Artwork/<UUID 앞 3자>/<나머지>/`. 아트워크 있는 곡이 전부 이 규칙과 일치했다.
- `djmdContent.ImagePath`는 그 안의 `artwork.jpg`다. 없으면 빈 값 `''`이다.
- `djmdAlbum.ImagePath`는 전부 NULL이다. DJCrate는 건드리지 않는다.
- 파일 셋은 스냅샷 사본과 share를 읽기 전용으로 조사해 확인했다. 대상은 아트워크 있는 곡 전부, 파일 19,914개다.
- `artwork.jpg`는 원본 크기 그대로이되, 긴 변이 800을 넘으면 800으로 줄인다.
  - 비율은 유지한다. 짧은 변은 반올림한다.
  - 예: 900×784 → 800×697, 3311×3001 → 800×725, 실험 곡 1200×900 → 800×600.
- `artwork_m.jpg` 240×240과 `artwork_s.jpg` 80×80은 정사각에 맞게 크기를 바꾼 뒤 남는 곳을 검은 여백으로 가운데 맞춘다. 200×200 원본도 240으로 키운다.
- 셋 다 원본이 JPEG여도 다시 인코딩한 기준선 JPEG다. PNG도 JPEG로 바꾼다.
- 머리 순서는 아래와 같다.

  | 조각 | 내용 |
  |---|---|
  | SOI | — |
  | APP0 | JFIF 1.01, 비율 1:1, 썸네일 없음 |
  | DQT 둘 | libjpeg 품질 85 휘도·색차 표 |
  | SOF0 | Y 2x2, Cb·Cr 1x1 |
  | DHT 넷 | DC0·AC0·DC1·AC1. 최적화라 그림마다 다름 |
  | SOS | — |

- EXIF·ICC는 없다. 19,914개 전부 같은 머리다.
- 파일 행(`contentFile`)은 `_m`·`_s` 없이 `artwork.jpg` 하나만 있다. 라이브러리에 6,637행이 있었다.
- 파일 행의 칸은 분석 파일 행과 같다.
  - ID: `<곡 UUID>_<경로, /는 %2F>`
  - MD5, 크기
  - `rb_local_path`
  - `rb_priority`: 50
- 실험 곡 행도 전 칸이 이 모양이다.
  - `rb_insync_hash`, `rb_insync_local_usn`, `rb_temp_path`, `usn`: NULL
  - 나머지 상태 칸: 0
  - `UUID`: 소문자 v4
  - `created_at` = `updated_at`
- 곡을 빼면 파일 셋을 지운다. 폴더는 남긴다. 근거는 "サラマンダー 복사본" 삭제 실험이다.

DJCrate(`TrackArtwork`·`ArtworkJPEG`):

- DJCrate는 아래 두 곡에 아트워크를 넣는다(`RekordboxTrackWriter.writesArtwork`).
  - **분석까지 붙여 넣는 곡**
  - **분석을 붙이는 분석 전 곡**
- 위 실험으로 2026-09-26에 열었다.
- 분석 없이 넣는 곡은 rekordbox처럼 넣지 않은 채, rekordbox에서 분석하면 생긴다고 확인 창에 알린다.
- 변경 번호는 오토게인 행 앞이다. 순서는 위 "추가(분석 포함)"와 아래 "분석 붙이기"에 있다. 시험은 `RekordboxTrackArtworkTests`·`RekordboxAnalysisArtworkTests`다.
- 크기·여백·머리는 같게 만든다. 그래도 바이트는 다르다.
  - 허프만 표가 그림마다 다르다.
  - 축소 방식과 DCT가 다르다.
- `djc lab artwork-check`로 라이브러리 곡의 음원 그림을 다시 만들어 비교했다(21곡).

  | 파일 | 결과 |
  |---|---|
  | `artwork.jpg` | 머리 같음. 화소 차이(0~255) 중앙 0.1·최대 1.1. 크기 비 0.997~1.009. 거의 같다 |
  | `_m`·`_s` | 축소 필터 차이로 중앙 4.4·8.1 |
  | 실험 곡 | 머리 같음. 화소 차이 0.1·2.5·4.9. 크기 비 1.001·0.95·0.99 |

- `_m`·`_s`의 축소 필터는 시험한 것 중 CoreGraphics 고품질이 가장 가까웠다.

확인하지 않은 것:

- 투명한 PNG. 지금은 검은 바탕에 그린다.
- EXIF 회전. 지금은 무시한다.
- 그림이 여럿일 때 고르는 그림. 지금은 AVFoundation이 주는 첫 그림을 쓴다.
- 분석 말고 다른 때 아트워크를 뽑는지. 예: 곡 선택, 덱에 올리기, 태그 다시 읽기.
- 라이브러리의 분석하지 않은 곡(`Analysed` 0)에도 아트워크가 있다. 넣을 때는 뽑지 않으므로 그런 다른 길이나 옛 버전에서 온 것으로 보인다.

분석 붙이기와 아트워크:

- 분석 붙이기(`RekordboxWriter+Analysis`, #87)는 위 실험의 "분석할 때"와 같은 경우다. 그래서 같은 파일 셋·`ImagePath`·파일 행을 넣는다(아래 "분석 붙이기").
- 이미 아트워크가 있는 분석 전 곡은 아트워크를 건드리지 않은 채 분석만 붙인다. rekordbox가 분석할 때 그림을 다시 뽑는지 확인하지 않았기 때문이다.
  - 이런 곡은 `ImagePath`나 아트워크 파일 행이 있는 곡이다. 곡 UUID 아트워크 폴더에 파일이 있는 곡도 같다.
- 라이브러리에는 `ImagePath`가 있으나 음원에 그림이 없는(파일에 `covr`가 없는) m4a가 있다.
- 이 곡은 rekordbox에서 직접 그림을 붙인 곡이나, 넣은 뒤 태그가 바뀐 곡으로 본다. DJCrate는 음원에 그림이 없으면 아트워크를 만들지 않는다.

**삭제**

삭제는 삭제 표시가 아니라 행을 실제로 지운다.

- 지우는 행은 아래와 같다.
  - 곡 행
  - 큐(`djmdCue`·`contentCue`)
  - 파일 행
  - 오토게인 행
  - 재생 목록·재생 이력 항목
- 같은 이력의 뒤 순번은 하나씩 당긴다. 그 행들은 한 변경 번호로 몰아 받는다. 재생 목록도 같다고 보고 당긴다(추정).
- 화면의 "플레이리스트에서 제거"는 남은 곡을 모두 다시 매긴다(아래 "재생 목록").
- 컬렉션에서 지울 때 재생 목록 항목이 어떻게 되는지는 아직 실험하지 않았다.
- 당기는 살아 있는 행의 동기화 상태는 재생 목록 편집(`touchEntry`)처럼 256 → 257로 올린다. 257·0은 그대로 둔다.
- 이것은 동기화 데이터를 DJCrate가 고친 행은 257이라는 사용자 정책이다.
- 재생 목록·이력의 순번을 당길 때의 동기화 상태 변화는 상태 0 시험 곡으로만 보았으므로 이 규칙은 [미확인]이다. 묶음 3 세션 D3에서 확인한다.
- 쓴 뒤에는 당긴 행도 다시 읽어 순번과 상태가 기대와 같은지 본다(`verifyRenumbered`).
  - 순번은 앞에서 지운 항목 수만큼 줄어든 값이다.
  - 상태는 256만 257로 바뀐다.
  - 곡 빼기는 커밋 뒤에 본다. 합치기는 트랜잭션 안과 커밋 뒤에 본다.
- 한 요청에서 여러 곡·여러 묶음이 같은 목록을 차례로 당길 수 있다. 이때 기대는 곡마다 덮어쓰지 않은 채 앞 곡의 기대에 이어 간다.
- 다르면 백업으로 되돌린다.
- 그 곡만 쓰던 아티스트·앨범 행도 지운다.
- 분석 폴더는 통째로 지운다. 아트워크는 파일만 지운 채 폴더는 남긴다.
- 아래 표에 걸린 곡은 안 막으면 지운 곡을 가리키는 행이 남으므로, 아직 지우지 않는다.
  - MyTag
  - 핫큐 뱅크
  - 샘플러
  - 관련 곡
  - 신청곡
  - 검열 구간
  - 클라우드 내보내기
  - 추천 좋아요(`djmdRecommendLike`). 곡을 가리키는 칸이 `ContentID1`·`ContentID2` 둘이다.
- 추천 좋아요는 `ContentID`가 아니라 두 칸 중 하나라도 걸리면 막는다(`unverifiedReferenceBlock`).
- 이 검사가 읽는 칸은 호환 확인(`requiredColumns`)에 있으므로, rekordbox 업데이트로 칸이 없어지면 백업 전에 막는다(#203).
  - 읽는 칸은 위 표들의 `ContentID`와 추천 좋아요의 `ContentID1`·`ContentID2`다.

## 분석 붙이기 (분석 전 곡, `RekordboxWriter+Analysis`, #6)

분석 붙이기는 라이브러리에 이미 있으나 분석 파일이 없는 곡에 분석 파일을 붙인다. 반영할 때 그 곡의 그리드 초안으로 분석 파일을 만든다. 레시피는 곡 넣기(분석 포함)와 같아서 `RekordboxTrackWriter.prepare`·`fileRow`·`mixerRow`를 쓴다.

쓰기는 `RekordboxWriter.write`의 안전 절차를 따른다.

1. 사전 확인
2. 백업
3. 한 트랜잭션
4. 다시 읽어 검증
5. 무결성 검사
6. 실패 시 복원

- 파일은 rekordbox 폴더에 있는 CRLF 줄 끝 파일이다. NODE 한 줄마다 아래 속성이 있다.

  | 속성 | 값 |
  |---|---|
  | `Id` | 목록 ID 16진수 대문자 |

- **만들기**: 끝에 Timestamp 0인 NODE를 붙인다. 이름을 붙이면 그 NODE와 부모 폴더의 Timestamp가 그 시각이 된다.

**DJCrate가 쓰는 것**

- `RekordboxWriter.write(playlists:)`가 편집(`PlaylistEdit`)을 적힌 순서대로 한 트랜잭션에서 쓴다. 번호를 받는 순서와 비우는 번호까지 위 표와 같게 한다.

- XML은 커밋·확인 뒤 적는다. 적지 못하면 DB·XML 모두 되돌린다.
- 백업에 XML을 함께 두어 되돌리기 때 같이 살린다. DB 옆에 XML이 없는 사본은 DB만 쓴다.

### 인텔리전트 재생 목록 읽기 (#68, 읽기만 · rekordbox 실험 전)

- rekordbox 7.2.18에서 직접 만든 인텔리전트 목록으로 확인한 것이 **아직 없다**.
- 2026-10-06에 본 최신 스냅샷 사본에는 `Attribute` 4 행도 `SmartList` 값도 없어, 실제 행으로 형식을 확인하지 못했다.
- 아래 형식은 쓰기 규칙이 아닌 [제3자] 자료다. 근거는 pyrekordbox(MIT)의 `masterdb/smartlist.py`와 `db6.md`다(`THIRD_PARTY_NOTICES.md`).

**형식**

- `SmartList`는 XML 글자다.
- `<NODE Id LogicalOperator AutomaticUpdate>` 아래 `<CONDITION PropertyName Operator ValueUnit ValueLeft ValueRight/>`가 줄지어 든다.
- `LogicalOperator`는 1 = 모두, 2 = 하나라도다.
- `Operator` 1~11의 뜻은 아래와 같다.

  | `Operator` | 뜻 |
  |---|---|
  | 1 | 같음 |
  | 2 | 같지 않음 |
  | 3 | 큼 |
  | 4 | 작음 |
  | 5 | 범위 |
  | 6 | 최근 N |
  | 7 | 최근 N 아님 |
  | 8 | 포함 |
  | 9 | 포함하지 않음 |
  | 10 | 시작 |
  | 11 | 끝 |

- `PropertyName` 값은 아래와 같다.

  | 칸 | 값 |
  |---|---|
  | `PropertyName` | `artist`, `album`, `albumArtist`, `originalArtist`, `bpm`, `grouping`, `comments`, `producer`, `stockDate`, `dateCreated`, `counter`, `fileName`, `genre`, `key`, `label`, `mixName`, `myTag`, `rating`, `dateReleased`, `remixedBy`, `duration`, `name`, `year` |

**읽기**

- `RekordboxLibrary`가 `Attribute` 4 행의 `SmartList`를 `SmartPlaylistSource`로 읽는다(`RekordboxPlaylist.smartSource`).
- 알려진 모양과 조금이라도 다르면 읽지 않은 채 이유만 남긴다. 다른 모양은 아래와 같다.
  - 모르는 칸
  - 중첩 NODE
  - 남은 글자
  - 결합 방식
  - 자동 갱신 값
- `isSmart`·곡 항목·편집 막힘은 읽기를 더하기 전과 같다.

**계산** (`SmartPlaylistEvaluator`, 순수 규칙)

- 지금은 아래 항목만 계산한다.

  | 항목 | 종류 | 연산자 |
  |---|---|---|
  | `name`·`artist`·`album`·`albumArtist`·`comments` | 글자 | 같음·같지 않음·포함·포함하지 않음·시작·끝 |
  | `year` | 숫자 | 같음·같지 않음·큼·작음·범위 |

- 값 단위는 빈 글자만 받는다.
- 그 밖의 항목, 연산자, 단위, 값 모양은 "지원하지 않는 조건"이다. 그런 조건이 하나라도 든 목록은 곡을 보이지 않는다.
- 아래 항목은 계산하지 않는다.

  | 항목 | 이유 |
  |---|---|
  | `bpm`·`duration` | 값이 DB 정수인지 화면 값인지 모른다 |
  | `genre`·`key`·`myTag`·`grouping` | 값이 이름인지 번호인지 모른다 |
  | 날짜·최근 N일 | 기준을 모른다 |
  | `rating`·곡 색·My Tag | 읽기가 #65·#67에서 들어온다 |

**확인 전 해석** (`SmartPlaylistSemantics.provisional`)

- 묶음 3 M1에서 rekordbox 곡 수와 견줘 정할 때까지의 해석은 아래와 같다.

  | 대상 | 해석 |
  |---|---|
  | 글자 | 대소문자 무시 |
  | 큼·작음 | 경계 제외 |
  | 범위 | 양끝 포함 |
  | 같지 않음·포함하지 않음 | 빈 값 포함 |

- 글자는 NFC로 맞춰 비교하되 전각·반각은 맞추지 않는다.
- `AutomaticUpdate`의 뜻은 모른다. 계산에 쓰지 않는다.
- 삭제된 곡은 뺀다. 스트리밍 곡은 포함한다. 결과 순서는 컬렉션 순서다.

**앱**

- 설정 › 실험실 › 인텔리전트 재생 목록 보기를 켰을 때만 계산해, 사이드바에 읽기 전용으로 보인다.
- 이 설정은 기본이 끔인 `SettingKeys.labSmartPlaylists` = `lab.smartPlaylists`다.
- 끄면 목록은 곡 없이 보여, 이 기능이 없던 때와 같다.
- 쓰기·USB 내보내기·XML 경로는 설정과 상관없이 인텔리전트 목록을 그대로 거른다.

## 재생 기록 (`RekordboxWriter+History`, #43)

이 절은 rekordbox 재생 기록(Histories)의 모양과 DJCrate의 쓰기 규칙이다. 2026-10-09에 아래 둘을 보았다.

- rekordbox 7.2.x 실제 라이브러리의 스냅샷 사본을 읽기 전용으로 질의했다.
- USB 기록 가져오기를 실험했다. 아래 "가져오기 실험"이다.

쓰기 경로는 이 실험과 사본 재현, 골든 시험으로 확인했다. 확인하지 않은 조건은 기록마다 막는다.

### 표의 모양 [확인]

**연·월 폴더** (`djmdHistory`, `Attribute` 1)

| 행 | ID | Name | `ParentID` |
|---|---|---|---|
| 연 폴더 | 연("2026") | 연 | "root" |
| 월 폴더 | 연+월 두 자리("202608") | 월 숫자("8", 앞 0 없음) | 연 폴더 |

- 화면은 월 폴더를 "8월"로 보인다.
- 연·월 폴더의 `Seq`는 만든 순서다.

**기록** (`djmdHistory`, `Attribute` 0)

- `ParentID`는 월 폴더다.
- `Seq`는 그 폴더 안 순서다. 1부터 센다.
- `DateCreated`는 로컬 시각 "yyyy-MM-dd HH:mm:ss"다.
- 화면은 연·월·기록을 모두 오래된 것부터 보인다.

**항목** (`djmdSongHistory`)

- 칸은 `HistoryID`·`ContentID`·`TrackNo`다. `TrackNo`는 1부터 센다.
- 같은 곡을 두 번 틀면 행이 둘이다.

**이름**

- USB에서 가져온 기기 기록과 PERFORMANCE 기록은 "HISTORY yyyy-MM-dd"다.
- PRO DJ LINK 기록은 "LINK HISTORY yyyy-MM-dd"다. LINK EXPORT 기록이 이것이다.
- 같은 이름이 있으면 뒤에 번호를 붙인다. 예: "HISTORY 2026-08-01 (1)"
- 같은 초에 만든 기록 셋이 있었다. 셋은 이름의 날짜도 같았다. USB 기록 여럿을 한 번에 가져온 흔적이다.
- USB 기록의 날짜는 가져온 날이다. 기기 기록에는 날짜 칸이 없다(`docs/usb-internals.md` §2.2·§3.5).
- 근거는 매뉴얼 JA의 "取り込んだ日付が付加されて"다(7.2.18 JA p.109).

**읽기**

- `RekordboxLibrary.loadHistories`가 폴더 행을 따로 읽는다.
- 기록마다 위 폴더 이름(`folderNames`)과 `Seq`를 붙인다. 예: ["2026", "8"]
- 앱 트리(`HistoryTree`)는 폴더 이름이 [연, 월] 숫자면 그것으로 연·월을 정한다. 아니면 `DateCreated`로 정한다.

### rekordbox의 가져오기 규칙 (매뉴얼·FAQ, #43 조사)

- EXPORT 모드에서 USB를 연결하면 자동으로 가져온다.
  - 설정은 Preferences › DJ System › Device › History의 "Import the play history automatically"다.
  - 기본은 켜짐이다.
- "Delete from the device after importing the play history"도 기본이 켜짐이다.
  - 그래서 기본 설정의 rekordbox는 가져온 기록을 USB에서 지운다.
  - 7.0.6 전에는 늘 지웠다.
- 이름과 내용이 같은 기록은 자동으로 다시 가져오지 않는다.
- 컬렉션에 없는 곡은 가져오지 않는다.
- PERFORMANCE 모드에서는 가져오지 않는다.
- 환경설정은 `~/Library/Application Support/Pioneer/rekordbox6/rekordbox3.settings`에 있다.
  - `importHistory`: 자동 가져오기
  - `DeleteHistoryWhenImported`: 가져온 뒤 기기에서 삭제
  - 이 Mac에서는 실험 전에 둘 다 기본값인 켜짐(1)이었다.

### 가져오기 실험 (2026-10-09, rekordbox 7.2.19.0342) [확인]

**조건**

- EXPORT 모드에서 했다.
- 환경설정 › DJ System › 장치 › 히스토리를 아래처럼 바꿨다.
  - "재생 히스토리 자동으로 들여오기": 켬
  - "Delete from the device after importing the play history": 끔
- USB는 Device Library에만 기록이 든 FAT32 USB다.
  - CDJ가 남긴 기록 하나가 있었다. 기록 이름은 흐렸다.
  - 곡은 "エクストラ・マジック・アワー" 1개다.
- USB를 꽂은 채 rekordbox를 켰다. rekordbox가 기록을 자동으로 가져왔다.
- 전후 스냅샷(`djc snapshot --force`)을 `djc lab db-diff`로 비교했다.

**새 월 폴더**

- 월 폴더가 없으면 새로 만든다.
- `djmdHistory` ID는 "yyyyMM"이다. 예: "202610"
- Name은 월 숫자("10")다. `Attribute`는 1이다.
- `ParentID`는 연 폴더 ID("2026")다.
- `Seq`는 그 연 폴더 안 다음 번호다.
- `DateCreated`는 로컬 "yyyy-MM-dd HH:mm:ss"다.
- **`UUID`는 ID와 같은 글자다.** 예: "202610"
- 연 폴더는 기존 행이었다. ID·Name·`UUID`가 모두 "yyyy"이고 `ParentID`는 "root"다.

**기록 행**

- ID는 숫자 글자다. 32비트 범위 난수 모양이다. 예: "2063847119"
- Name은 가져온 날의 "HISTORY 2026-10-09"다.
- `Attribute`는 0이다. `ParentID`는 월 폴더다.
- `Seq`는 그 월 폴더 안 다음 번호다.
- `DateCreated`는 로컬 시각이다. `UUID`는 소문자 v4 UUID다.

**항목 행** (`djmdSongHistory`)

- **ID는 소문자 v4 UUID 글자다.**
- `HistoryID`, `ContentID`, `TrackNo`를 적는다. `TrackNo`는 1부터 센다.
- `UUID`는 또 다른 v4 UUID다.

**새 행 셋의 공통 칸**

- `rb_data_status`와 `rb_local_data_status`는 0이다.
- `rb_local_deleted`와 `rb_local_synced`도 0이다.
- `usn`은 NULL이다. `created_at`·`updated_at`은 UTC ms다.

**곡 행**

- 기록에 든 곡의 `djmdContent` 행이다.
- **`DJPlayCount`(정수)가 1 늘었다.**
- `TrackInfoUpdated`(글자)도 1 늘었다.
- `rb_local_usn`과 `updated_at`이 바뀌었다.
- 그 밖의 칸과 표는 그대로였다. `djmdProperty`도 그대로였다. 인증 표는 비교하지 않았다.

**변경 번호**

- 순서는 월 폴더 → 기록 → 기록 항목 → 빈 번호 하나 → 곡 행이다.
- 곡 행 앞의 빈 번호는 태그 저장과 같은 모양이다.

**USB**

- rekordbox는 기록을 지우지 않았다. 대신 `PIONEER/rekordbox/ImportedHistory.xml`을 새로 썼다(`docs/usb-internals.md` §8.5).
- 이 USB는 동기화가 켜져 있었다(`playlists3.sync` AutomaticSync 1). 그래서 rekordbox가 연결 때 목록도 다시 내보냈다.
  - DB 셋을 다시 썼다. 기록 표는 그대로였다.
- `masterPlaylists6.xml`도 같은 때 바뀌었다. 실험 전 사본이 없어 기록 가져오기 때문인지 모른다.

**확인하지 못한 것** [미확인]

- 같은 곡이 기록에 두 번 들 때 `DJPlayCount`가 몇 느는지
- 컬렉션에 없는 곡만 든 기록
- 연 폴더를 새로 만들 때의 `Seq`
- OneLibrary 기록
- 기록 ID를 짓는 규칙

### DJCrate가 쓰는 것 (`RekordboxWriter.write(histories:)`)

- 위 실험의 행을 그대로 쓴다.
- 쓰기 관문은 `RekordboxWriter.writesHistories`다. 지금 열려 있다.
- 2026-10-09에 사본 재현으로 확인한 뒤 열었다. 아래 "사본 재현"을 본다.

**순서**

- 행 순서는 월 폴더 → 기록 → 항목 → 곡 행이다. 월 폴더는 없을 때만 만든다.
  - 항목은 `TrackNo` 순이다. 곡 행은 처음 나온 순이다.
  - 행마다 변경 번호를 하나 받는다.
- rekordbox가 곡 행 앞에 두는 빈 번호는 두지 않는다. 번호 값은 비교하지 않는다.
- 연 폴더가 없으면 막는다.

**칸 값**

- 컬렉션에 없는 곡은 쓰지 않는다. 없는 곡과 지운 곡이 여기에 든다(rekordbox 매뉴얼).
- 남은 항목의 `TrackNo`는 1부터 다시 매긴다.
- 같은 이름의 살아 있는 기록이 있으면 " (n)"의 가장 작은 빈 번호를 붙인다.
  - 이름이 이미 " (n)"으로 끝나면 그 번호를 뗀 이름으로 센다.
  - 지운 기록의 이름은 세지 않는다.
- 기록 ID는 `UInt32` 난수다.
  - 7자리 미만이면 다시 뽑는다. 그래서 연·월 폴더 ID와 겹치지 않는다.
  - 기존 ID와 겹쳐도 다시 뽑는다.
- `Seq`는 살아 있는 자식의 가장 큰 값 + 1이다.
- `DateCreated`는 DJCrate가 USB에서 보존한 시각이다. 기록과 새 폴더가 같다.
- `created_at`·`updated_at`은 쓰는 시각이다. rekordbox에서는 두 시각이 같은 순간이다.
- 이미 있는 월 폴더 행은 고치지 않는다. 실제 폴더 행은 모두 `created_at` = `updated_at`이다.

**다시 확인하는 것**

- 앱은 쓰기 입력에 컬렉션 DBID와 USB 원본 곡 키를 함께 넘긴다.
- 쓰기는 백업 전과 트랜잭션 안에서 대상 곡의 원본 식별을 다시 확인한다.
- 최신 대상에 같은 기록이 이미 있으면 `unchanged`를 돌려준다.
  - 같은 기록은 이름·날짜·전체 곡 순서가 같은 기록이다. 보존본에 남은 쓴 ID를 검증한 기록도 같은 기록이다.
  - DB와 재생 횟수는 그대로 둔다. 앱은 보존본의 연결만 고친다.
- `djmdHistory`·`djmdSongHistory`는 `exactColumns`에 있다.
  - 칸이 바뀌면 모든 쓰기가 막힌다. 재생 목록 표와 같은 정책이다.

**막는 것**

아래 기록은 백업 전에 막는다. 다른 기록과 초안은 그대로 쓴다.

- 같은 곡이 두 번 이상 든 기록. 재생 횟수가 몇 느는지 확인하지 않았다.
  - 앱은 이 기록을 쓰기 대기에 올리지 않는다(`HistoryWriteQueue`).
- `rb_data_status`가 0이 아닌 곡이 든 기록. 동기화 곡은 확인하지 않았다.
- `DJPlayCount`가 NULL인 곡이 든 기록
- 새 연 폴더가 필요한 기록
- 한 쓰기에서 같은 곡이 여러 기록에 든 경우. 해당 기록을 모두 막는다.
- 컬렉션 곡이 하나도 없는 기록
- 연·월 폴더 자리에 아래 행이 있는 기록
  - 폴더가 아닌 행
  - 부모가 다른 행
  - 지운 행
- 같은 쓰기에 같은 곡의 태그 초안, 그림 초안, 합치기가 있는 기록
- 이름이 빈 기록
- 날짜가 없는 기록

**열어 두었으나 실험하지 않은 것** [미확인]

실험은 곡 1개가 든 기록 하나였다. 아래 경우는 막지 않고 쓴다. 규칙은 위 실험의 모양을 넓혀 적용한 것이다.

- 서로 다른 곡이 여러 개 든 기록. 항목·곡 행의 변경 번호 순서는 곡 1개로만 보았다.
- 이미 있는 월 폴더에 기록을 더하는 경우. 기록 `Seq`는 읽기 전용 관찰에서 얻은 "가장 큰 값 + 1"이다.
- 보존한 날의 달 폴더가 없는 경우. 지난 달이어도 그 달 폴더를 새로 만든다. 폴더 `Seq`도 "가장 큰 값 + 1"이다.
- 같은 쓰기에 같은 곡의 큐·그리드 초안이 있는 경우. 곡 행의 마지막 변경 번호는 합성 시험으로만 보았다.

### 사본 재현 (2026-10-09)

- 명령은 `djc lab history-repro --old <실험 전 사본> --new <실험 뒤 사본> --work <새 폴더>`다.
- 마지막 줄은 "기록 재현: 차이 0"이었다. SQLite 저장 형식까지 차이가 없었다.
- 이 도구는 아래를 비교한다.
  - SQLite 저장 형식
  - 모든 칸 값
  - 변경 번호 순서
- 아래만 비교에서 뺀다.
  - 난수 ID·UUID 값. 모양은 본다.
  - 실행 시각
  - 변경 번호 값
- 인증 표와 칸은 읽지 않는다.
- 비교할 기록이 없으면 실패로 끝난다. 차이가 있어도 실패로 끝난다.
- `--work`는 임시 폴더 아래의 빈 폴더만 받는다(`LabWorkFolder.check`). 실제 라이브 DB로 이어지는 링크도 거부한다.
- 골든 시험은 `Tests/RekordboxKitTests/HistoryWriteTests.swift`다. 이 실험의 칸 값을 기대값으로 둔다.

아래는 rekordbox에서 새로 분석한 전후 비교가 아니라, 기존 스냅샷을 읽은 결과다.

- **[확인]** AudioToolbox에서 확인한 형식은 `aac `·`paac`, ffprobe에서는 `aac`였다. `alac`는 찾지 못했다.

## ALAC·비LAME VBR 분석 파일 조사 2 (#8·#9, 2026-09-27)

- **ALAC 16/24비트·44.1/48kHz 스테레오**

확인한 방법은 아래와 같다.

**[확인] 실험 조건**

- rekordbox 7.2.18에 합성 7곡만 기본 자동 분석으로 가져왔다.

- 여기서 비LAME은 압축 라이브러리의 출처가 아니라 첫 정보 프레임 문자열에 따른 분류다.
- 스냅샷은 가져오기 직후 분석 전, 분석 완료, 앱 종료 후의 셋을 보존했다. 분석 파일은 실제로 복사한 사본으로 비교했다.
- 업데이트·OneLibrary 변환·기존 곡 편집은 하지 않았다.

|---|---:|---:|---:|---:|---:|---:|
| DJC 실험 ALAC 16bit 44100Hz | 6 | 195 | 16 | 44100 | 33 | 5007 |
| DJC 실험 ALAC 16bit 48000Hz | 6 | 234 | 16 | 48000 | 33 | 5007 |

**[확인] ALAC**

- `BitRate`는 `kAudioFilePropertyBitRate`의 bps를 1000으로 나눈 버림이다. 예: 195046, 234701, 901640, 984708 → 표의 값.
- `mBitsPerChannel`은 0이다. 비트 깊이는 `mFormatFlags`의 원본 16/24비트 플래그로 판별한다.
- 확장자만으로 AAC와 구분할 수 없다.
- 태그 순서는 아래와 같다.

  | 파일 | 태그 순서 |
  |---|---|
  | `.DAT` | `PPTH PVBR PQTZ PWAV PWV2 PCOB PCOB` |
  | `.EXT` | `PPTH PWV3 PCOB PCOB PCO2 PCO2 PQT2 PWV5 PWV4` |
  | `.2EX` | `PPTH PWV7 PWV6 PWVC` |

- `PVBR` 머리·400칸·끝값이 모두 0이다. `PVB2`는 없다. `PPTH`는 `?/파일 이름`이다.
- 33.375초 표본의 `PWV3·PWV5·PWV7`은 유효 샘플만 센 `ceil(길이×150)`과 같은 5007칸이다.
- 프라이밍은 0이며 끝 패딩은 더하지 않는다. `Length`는 초 버림이다.
- 이번 확인 범위는 스테레오 16/24비트·44.1/48kHz다.

**[확인] 비LAME VBR**

- 기존 스냅샷의 `Xing Lavc/Lavf` 표본과 새 합성 3곡에서 `BitRate`는 정보 프레임을 뺀 **첫 음성 프레임**의 비트레이트였다.
- 이 값은 정보 프레임 비트레이트·Xing 평균 비트레이트와는 달랐다.
- `PVBR`에 정보 프레임을 뺀 `n`개 프레임으로 기존 식 `max(0, floor((k+1)×n/400)−8)`을 쓰면, 400칸과 끝값이 바이트까지 같다.
- 새 44.1kHz 표본의 끝값은 1473408샘플, 48kHz는 1603584샘플이다. 상세 파형 5012칸은 `ceil(센 MPEG 샘플×150/sampleRate)`와 같다.
- `Xing L3.99r1`은 같은 후보식에서 PVBR이 달랐다. 파형도 4칸 길었다.
- 2026-10-03(#14 곡 F)에 정보 프레임을 LAME처럼 세자 PVBR 400칸·끝값·파형 길이가 맞았다. 위 "MP3 프레임 세기"를 본다.
- 이 인코더의 분석 쓰기는 비트레이트 0·시간축 보정·사본 재현을 아직 확인하지 않아 막는다.
- 알 수 없는 인코더·Xing이 아닌 머리도 새 규칙으로 인정하지 않는다. 음원 누락은 일치와 구분해 제외했다.
- 읽기 전용 재현은 `djc lab nonlame-vbr-check --db <스냅샷>`이다.
- 이 명령은 인코더, 비트레이트 후보, PVBR 일치 여부, 파형 길이 차이의 중복 없는 익명 수치만 출력한다. 곡 이름·경로·곡 수는 출력하지 않는다.

**[확인] 사본 재현과 남은 불일치**

- 파일 행은 신원, 해시, 크기, 변경 번호, 시각을 뺀 채 비교하면 `.3EX` 행이 없는 것 말고 같다.
- 오토게인은 0.1dB 안이다.
- 분석 파일은 태그 순서, PPTH, PVBR, PCOB, PCO2, 파형 길이가 같다.
- rekordbox 그리드를 넣은 ②에서 32·48kHz `PQTZ`는 바이트까지 같다.
- 44.1kHz 대조본은 기존 44.1kHz와 같은 차이로, 정밀 시각이 ms 경계에 붙은 51박이 1ms 다르다.
- ①은 32kHz의 박 번호(마디 위치)만 달랐다. ①은 강세 없는 클릭이다.
- 그래서 32·48kHz ffmpeg Xing VBR 분석 쓰기를 연다(`AnalysisFormatGoldenTests`).
- MPEG-2 샘플레이트(16·22.05·24kHz, 576샘플 프레임)는 실험하지 않아 막는다.

**[확인] #14 재분석**

원래 곡 표기는 #14 이슈와 같다.

- **곡 B·C**(CBR MP3): 복제본의 새 분석은 DJCrate 계산과 PVBR·비트레이트가 같다.
  - 원래 곡의 PVBR 미기록(0)과 정보 프레임 포함은 옛 분석 상태다.
- **곡 D·E**(FLAC): 위 "곡 추가"의 PVB2를 본다.
  - 곡 E는 분석 뒤 파일이 바뀌었다.
  - 곡 D는 CRC-16이 맞지 않는 프레임 때문에 rekordbox 규칙이 달라 DJCrate가 분석을 막는다.
- **곡 F**(L3.99r1 VBR MP3): 위 "파일 형식별 탐색 위치"·"MP3 프레임 세기"를 본다. 정보 프레임을 세도록 고쳤다.
- 다시 돌린 대조의 결과는 아래와 같다.
  - `pvbr-check`·`pvb2-check`: 어긋남 0. 대상은 새 분석 파일 사본이다.
  - `seekinfo-check` FLAC·VBR 큐: 어긋남 0
- 라이브러리 FLAC 전체 `pvb2-check`는 위 "곡 추가"를 참고한다.

## 막아 둔 것 (규칙 미확인)

- **미확인 ALAC·VBR 형식의 분석 쓰기**: 아래는 계속 막는다.
  - ALAC 16/24비트·44.1/48kHz·스테레오 밖
  - MPEG-1(32·44.1·48kHz)이 아닌 ffmpeg VBR
  - L3.99r1·알 수 없는 비LAME VBR
- **CRC-16이 맞지 않는 프레임이 있는 FLAC의 분석 쓰기**: rekordbox의 PVB2 규칙이 손상 모양에 따라 갈렸다(#14). 위 "곡 추가"를 본다.
  - 잘린 프레임 1곡은 그 프레임을 뺀 채 이어 매겼다.
  - CRC만 틀린 프레임 12개 1곡은 머리 번호를 따랐다.
  - 규칙은 #193 이슈에서 확인한다.
- **반쪽 분석 곡의 그리드·분석 붙이기**: 반쪽 분석 곡은 .DAT만 있는 곡이다. .EXT는 없다.

## 중복 곡 합치기 (#63)

- `RekordboxWriter.write(merges:)`는 검증한 큐 쓰기·재생 목록 편집·곡 삭제를 한 트랜잭션으로 조합한다.
- 새 DB 칸의 쓰기 규칙은 추가하지 않는다.
- 합성 사본 시험 `DuplicateMergeWriterTests`는 큐·목록·삭제 도중 오류가 나면 전체를 롤백하는지 본다. DB·분석 파일·초안 복원도 본다.
- 실제 화면에서 합치기 전체를 확인하는 일은 별도다.

**초안과 큐**

- `DuplicateMergeDraft`는 남길 곡·뺄 곡과 준비 당시의 상태 지문을 저장한다.
- 아래가 바뀌면 쓰지 않는다.
  - 관련 곡, 큐, 파일, 게인, 이력 행
  - 관련 재생 목록 전체
  - 음원의 SHA-256
- 여러 묶음은 트랜잭션 시작 상태에서 한꺼번에 검사한다.
- 큐는 새 곡의 시간축으로 `대상 offset − 원본 offset`만큼 옮긴다.
- 읽을 수 있는 PCM·FLAC·AAC와 확인한 MP3 시간축만 허용하되, 실제 길이 차이가 20ms를 넘으면 막는다.
- 동일 음원 여부는 사용자가 확인한다. 오디오 지문으로 동일 음원임을 판정하는 기능은 없다.
- 이름, 종류, ms 시각, 루프 정보가 같은 큐만 하나로 합친다.
- 아래 경우는 막는다.
  - 서로 다른 핫큐가 같은 슬롯을 쓴다.
  - 활성 루프가 충돌한다.
- 메모리 큐 한도와 옮긴 큐의 범위를 검사한다.
- 뺄 곡의 자동 큐와 큐 색은 옮기지 않는다. 남길 곡의 자동 큐는 그대로 남는다.

**재생 목록과 삭제**

- 재생 목록에 남길 곡이 있으면 그 항목과 반복을 보존한 채 뺄 곡의 항목을 제거한다.
- 남길 곡이 없으면 첫 삭제 항목의 자리를 기억한 뒤 **빼기 → 끝에 넣기 → 순서 바꾸기**로 옮긴다.
- 인텔리전트 목록은 막는다.
- 삭제는 `RekordboxTrackWriter.deleteRow`의 기존 규칙을 공유한다. `unverifiedReferenceTables` 중 하나에 참조가 있으면 해당 묶음을 막는다.

**동기화 상태 원본은 막는다** (#196)

세션 D3 실험 전까지 막는다. 위 "곡 추가·삭제"의 삭제를 본다.

- 초안을 만들 때(`prepareMerge`)와 쓸 때의 사전 검사(`checkMergeReferences`)에서 검사한다. 사전 검사는 어떤 편집보다 먼저 한다.
- 검사는 지울 원본의 아래 상태를 본다.
  - 곡 행 상태
  - 딸린 행 상태. 목록 편집이 `deleteRow`보다 먼저 지우므로 재생 목록 항목도 여기서 본다.
  - 그 곡만 쓰던 앨범·아티스트 행 상태
- 함께 빠지는 다른 원본도 빠진 것으로 센다.
- 아래 중 하나라도 걸리면 그 묶음만 막는다.
  - 상태가 하나라도 0이 아니다.
  - 확인하지 않은 표(추천 좋아요 포함)에 걸렸다.
  - 이력의 뒤 순번을 당길 자리에 지운 표시 행이 있다.
- 안내는 "뺄 곡 ‘원본 이름’: … rekordbox에서 직접 빼세요"다. 보고의 제목은 남길 곡이므로 이유에 지울 원본의 이름을 적는다.
- 재생 목록은 목록 편집이 살아 있는 행만 다시 매기므로(256 → 257) 뒤 순번의 지운 표시 행은 보지 않는다.
- 지우는 자리(`deleteRow`)도 같은 검사를 한 번 더 한다. 거기서 막혀도 SAVEPOINT와 변경 번호를 되돌려 앞서 쓴 큐·목록 편집이 남지 않는다.
- 합치기 초안의 `base` 지문(`mergeFingerprint`)에는 확인하지 않은 표를 넣지 않는다. 그 표들은 걸리기만 해도 막으므로 지문이 아니라 쓸 때 사전 검사가 본다.

**남는 곡은 막지 않는다.** 남는 곡은 확인한 두 경로로만 고친다.

- 곡 행·큐는 동기화 곡의 `rb_data_status` 256 → 257을 실험으로 확인한 큐 쓰기로 고친다. 근거는 위 "동기화 상태(256·257)인 곡"과 "큐"에 있다.
- 재생 목록 항목은 위 "재생 목록"의 #38 실험으로 확인한 재생 목록 편집(넣기·순서 바꾸기)으로 고친다.
- 남는 곡이 256이어도 합쳐 257이 되는 것을 `SyncedTrackRemovalTests`가 본다.
- 아래는 옮기지 않은 채 확인 창에 알린다.
  - 재생 기록, 재생 횟수
  - 평점, 색, 마이 태그
  - 그리드, 게인

**되돌리기와 동시 반영**

- 한 묶음의 큐·목록·삭제 중 하나가 막히면 그 묶음 전체를 되돌린다.
- 분석·그림 파일은 커밋 전에 백업해 두었다가 DB 검증 뒤 지운다. 파일 삭제가 실패해도 자동 복원한다.
- 파일 정리는 아래 UUID 경로 규칙을 따른다. 경로가 다르면 파일은 남긴 채 결과에 알린다.
- 음원은 읽기만 한다.
- 같은 곡의 다른 초안이나 재생 목록 초안과는 동시에 반영하지 않는다. 기존 초안은 먼저 반영이나 버리기로 정리한 뒤 합친다.
- 성공한 합치기 초안은 백업 옆에 남겨 ‘반영 되돌리기’ 때 다시 살린다.

## 곡 삭제·합치기·되돌리기의 파일 경계

`RekordboxWriter+FileOwnership`은 곡 UUID로 두 폴더 경로를 만든다.

| 폴더 | 대상 파일 |
|---|---|
| `PIONEER/USBANLZ/<앞 3자>/<나머지>/` | `ANLZ0000.DAT`·`.EXT`·`.2EX`·`.3EX` |
| `PIONEER/Artwork/<앞 3자>/<나머지>/` | `artwork.jpg`·`artwork_m.jpg`·`artwork_s.jpg` |

- DB 경로의 부모 폴더가 이 경로와 정확히 같을 때만 표의 대상 파일을 정리한다.
- 심볼릭 링크, 음원으로 쓰는 경로, 다른 곡이 공유하는 폴더는 건드리지 않는다.
- 다른 파일이 섞여 있으면 그 파일은 남긴다. 곡 폴더가 비었을 때만 폴더도 지운다.
- 경로가 맞지 않아도 컬렉션에서는 빼되, 결과에 ‘분석 파일을 지우지 않음(경로가 예상과 다름)’을 남긴다.
- 파일은 DB 커밋 전에 백업한다. 삭제가 실패하면 DB와 파일을 함께 복원한다.
- 백업 복원은 DB를 바꾸기 전에 아래 규칙으로 모든 파일을 검증한다.

**복원 검증**

- `anlz/manifest.json`과 보고서의 `createdFiles`·`removedFiles`는 `share` 기준 상대 경로로 저장한다. 예: `PIONEER/USBANLZ/…`, `PIONEER/Artwork/…`.
- 쓰기 API가 돌려주는 보고서는 기존처럼 절대 경로다. 옛 절대 경로는 지정한 share 안에 있을 때만 받아들인다.
- 표기만 다른 같은 폴더는 비교 전에 한 표기로 맞춘다(`URL.comparablePath`, #136). 예: 임시 폴더의 `/tmp`·`/private/tmp`, `/var`·`/private/var`.
- 아래가 있으면 복원을 거부한다.
  - `..`
  - 심볼릭 링크
  - 중복 대상
  - 허용하지 않은 파일명
  - 손상된 메타데이터
  - 없는 백업 원본
- 복원할 DB의 UUID·경로와 같은 파일명 허용 목록도 확인한다.
- 앱의 되돌리기와 `djc rekordbox-restore`는 같은 검증을 쓴다. 사본 DB 옆에 share가 없다면 CLI에 `--share <폴더>`를 명시한다.
- 모든 검증을 통과한 뒤에만 복원 직전 백업을 만든 뒤 DB·파일을 바꾼다.

**연쇄 복원(#222)**

- 백업은 DB 전체와 그 쓰기가 바꾸는 분석·그림 파일만 담는다.
- 그래서 가장 최근이 아닌 백업으로 되돌릴 때는 아래 순서를 따른다.
  1. 그 뒤에 뜬 백업의 파일을 최신부터 차례로 되돌린다. 대상은 쓰기 백업, 곡 넣기·빼기 백업, 복원 직전 백업이다(`laterBackups`).
  2. 고른 백업의 파일을 되돌린다.
- DB·`masterPlaylists6.xml`은 고른 백업 것 하나만 쓴다.
- iTunes 동기화만 담은 백업은 DB·분석 파일을 바꾸지 않으므로 사슬에서 뺀다. `playlists3.sync`는 되돌리지 않는다.
- 순서는 이름의 시각(초)을 먼저 보고, 같은 초면 폴더를 만든 시각을 본다.
- 이름 끝(`-write`·`-delete`·`-before-restore`)은 뜬 순서와 상관이 없다. 백업 폴더 밖의 백업은 이름에 시각이 있어야 한다.
- 모든 단계는 바꾸기 전에 확인한다.
- 지울 파일의 소유권은 그 단계에서의 DB로 본다. 첫 단계는 지금 DB, 그 뒤는 바로 앞 백업의 DB다. 파일이 있는지는 앞 단계를 되돌린 뒤 상태로 센다.
- 뒤 백업 하나라도 다른 라이브러리이거나 되돌릴 수 없으면 그 백업 이름과 이유를 알린다. 이때 복원 직전 백업도 만들지 않는다.
- 복원 직전 백업에는 두 가지를 둔다.
  - 복원이 건드릴 파일의 지금 내용(`anlz/`)
  - 복원이 새로 만들 파일(보고서 `createdFiles`)
- 그래서 그 백업으로 되돌리면, 복원이 되살린 지운 곡의 파일을 지우는 것까지 분석·그림 파일이 복원 전으로 돌아온다.
- 복원 도중 실패하면 DB·XML·건드린 파일을 복원 전으로 돌린다. 그것도 못 하면 복원 직전 백업으로 되돌릴 명령을 알린다.
- rekordbox가 직접 바꾼 분석 파일은 어느 백업에도 없어 되돌리지 않는다. 이 일은 시점 스냅샷 #220이 맡는다.
- 고른 백업 뒤에 시점 스냅샷 복원이 있으면 거부한다. 아래 "시점 스냅샷으로 복원"을 본다.
- 앱은 확인 창에 함께 되돌릴 뒤 백업 수를 알린다. 되살리는 초안은 고른 백업 것뿐이다.

**백업 정리(#221)**

- 백업을 만드는 모든 경로가 끝에 `prune`을 부른다. 경로는 쓰기, 곡 넣기·빼기, iTunes 동기화, 복원이다.
- 같은 초의 `-2`…를 포함해 쓰기 백업(`-write`·`-add`·`-delete`)만 센다.
- 쓰기 백업이 `backupsToKeep`개를 넘으면 남길 가장 옛 쓰기 백업보다 옛 백업을 모두 지운다.
- 복원 직전 백업은 세지 않으므로 쓰기 백업을 밀어내지 않는다.
- 사이의 것은 지우지 않으므로 위 사슬이 끊기지 않는다. 시험은 `RekordboxBackupPruneTests`다.
- 회귀 시험은 `RekordboxRestoreChainTests`다. 아래 경우를 본다.
  - 다른 곡 그리드 두 번
  - 쓰기 뒤 같은 초에 곡 빼기
  - 복원 뒤 더 옛 백업으로 복원
  - 망가진 뒤 백업 거부
  - 도중 실패 되돌림

**파일 경계 회귀 시험**

회귀 시험은 `RekordboxDeletionFilesTests`다. 아래 경우를 본다.

- 음원 폴더를 가리키는 분석 경로
- 다른 UUID 폴더
- 폴더·파일 심볼릭 링크
- 다른 파일이 섞인 폴더
- 옛 백업의 잘못된 복원·삭제 경로

임시 폴더 사본의 네 표기도 같은 규칙으로 통과·거부하는지 본다(`RekordboxTempCopyPathTests`). 모두 음원을 보존한 채 합성 파일과 DB 사본으로 확인한다.

## 시점 스냅샷 (`RekordboxPointSnapshot`, #220·#223·#224)

쓰기 전 백업은 DB 전체와 그 쓰기가 바꾸는 파일만 담으므로 옛 백업은 연쇄로 되돌려야 한다(위 "연쇄 복원"). 시점 스냅샷은 DJCrate가 쓰는 파일 전체를 한 시점으로 담아, 다른 스냅샷 없이 혼자 그 시점으로 되돌린다(#223 결정, 2026-10-07).

**담는 것**

- `master.db`
- `masterPlaylists6.xml`
- `playlists3.sync`
- `share/PIONEER/USBANLZ/`
- `share/PIONEER/Artwork/`

rekordbox 폴더의 그 밖 파일과 음원은 담지 않는다. 예: `*.edb`, `networkAnalyze6.db`, `master.backup*.db`.

**저장**

- 저장 위치는 DJCrate 데이터 폴더의 `point-snapshots/<UTC 시각>Z-<종류>/`다. 사본 DB면 그 옆 `point-snapshots/`에 둔다.
- 복사는 `FileManager.copyItem`이 하므로 같은 APFS 볼륨이면 클론이다. 처음엔 공간을 거의 쓰지 않은 채 바뀐 만큼만 는다.
- 다른 볼륨이면 전체 복사가 된다는 것을 창·CLI가 알린다.
- DB에 클라우드 토큰이 들어 있으므로 권한은 폴더 0700·파일 0600이다. 내용은 출력·로그하지 않는다.

**뜨기**

- rekordbox·rekordboxAgent가 꺼진 채 WAL이 비었을 때만 뜬다. `.partial-<UUID>`에 다 뜬 뒤 이름을 붙인다.
- 뜨는 동안 아래 일이 생기면 버린다.
  - `master.db` 크기·수정 시각이 바뀐다.
  - rekordbox가 켜진다.
- 복원이 폴더 밖을 가리키는 링크를 되살리지 않도록 분석·앨범아트 폴더 안의 심볼릭 링크는 거부한다.
- 뜬 DB는 `quick_check`·`cipher_integrity_check`를 거친다.
- `snapshot.json`에 아래를 적는다.
  - 이름
  - 종류: 수동, 자동, 복원 직전
  - UTC 시각
  - 고정 여부
  - `djmdProperty.DBID`
  - 변경 카운터 두 개(`agentRegistry` 정수 칸만)
  - 곡 수
  - 담은 항목
  - 클론 여부
- 대상 DB·share는 라이브 기본 인자 없이 부르는 쪽이 적는다.
- 대상은 시험 프로세스의 실제 라이브러리를 거부하는 `resolveShareRoot`를 지난다(#182).

**보존**

| 종류 | 남기는 것 |
|---|---|
| 수동·고정 | 지우지 않는다. 사용자가 지울 때만 지운다. 고정은 푼 뒤 지운다 |
| 자동(#228) | 최근 N일. N일보다 오래된 것 중 가장 최근 하나(#236) |
| 복원 직전 | 고정하지 않은 최근 3개 |

- N일은 설정 › 저장 공간에서 정한다. 기본은 7일이다.
- #236의 하나는 라이브러리를 오래 두다 바꿔도 바꾸기 직전 상태가 남게 하려는 것이다. 고정한 것도 세므로 그것이 가장 최근이면 고정이 그 몫을 한다.
- 스냅샷마다 전체를 담아 서로 기대지 않으므로 어느 것을 지워도 남은 스냅샷의 복원은 끊기지 않는다. #221의 연쇄 문제가 생기지 않는다.
- 쓰기 전 백업과는 따로 정리하되, 목록은 창(rekordbox › 시점 스냅샷…)과 `djc snapshot-point list`에서 함께 보인다.

**시험**: `RekordboxPointSnapshotTests`가 합성 사본으로 아래를 본다.

- 범위, 권한, 클론 독립
- rekordbox 켜짐, WAL, 링크
- 실제 라이브러리 거부, 보존 정리

### 자동 시점 스냅샷 (`RekordboxPointSnapshot.takeAutoIfDue`, #228)

- 앱이 켜져 있는 동안 `AutoPointSnapshotRunner`가 메인 액터 밖에서 낮은 우선순위로 본다. 켠 뒤 90초에 처음 본 뒤 10분마다 본다.
- 보는 일은 스냅샷 폴더 목록과 `master.db` 파일 정보뿐이다. 라이브 DB는 열지 않는다.

**뜨는 조건**

아래 조건이 모두 맞아야 뜬다. 순서대로 본다.

1. 설정 › 저장 공간 "하루 한 번 자동 시점 스냅샷"이 켜져 있다. 기본은 켬이다.
2. DJCrate가 rekordbox에 쓰는 중이 아니다.
3. rekordbox·rekordboxAgent가 꺼져 있다. 사본이어도 자동은 켜져 있으면 뜨지 않는다.
4. WAL이 비어 있다.
5. 그날(사용자 달력) 자동 스냅샷이 없다.
6. 마지막 스냅샷의 원본 도장과 지금 `master.db`가 다르다. 스냅샷 종류는 상관없다.
7. 클론이 된다. 같은 볼륨이 아니면 뜨지 않는다.

- 원본 도장은 뜰 때의 `master.db` 크기·수정 시각을 담은 `snapshot.json`의 `source`다.
- 도장 없는 옛 스냅샷은 그 안의 `master.db` 크기·수정 시각으로 견준다. 복사·클론은 수정 시각을 그대로 두므로 바뀌지 않았으면 같다.
- 견줄 수 없으면 바뀐 것으로 보고 뜬다.
- 클론이 안 되면 큰 복사를 몰래 하지 않도록 뜨지 않은 채 설정에 이유를 보인다.

**뜨기와 정리**

- 뜨기는 수동과 같은 `take`를 지난다. `take`가 하는 일은 아래와 같다.
  - 대상 확인
  - rekordbox 꺼짐 확인
  - WAL 확인
  - 링크 거부
  - 뜨는 동안 바뀌면 버림
- 뜨든 건너뛰든 보존 정리를 한다. 자동만 일수로 정리한다. 수동·고정·복원 직전은 대상이 아니다.
- 뜨는 동안 DJCrate가 rekordbox에 쓰기 시작하면(`LibraryStore.rekordboxWriteCount`) DB와 분석 파일이 다른 시점일 수 있다. 그래서 그 스냅샷을 버린 뒤 다음에 다시 뜬다.

**알림과 거르는 실행**

- 확인 창과 성공 알림 없이 조용히 한다. 실패는 표준 오류에 남긴다.
- 일부 실패만 앱을 켠 동안 한 번, 작은 토스트로 알린다.
  - 뜨는 도중 rekordbox가 켜진 실패는 알리지 않는다.
  - DJCrate 쓰기가 끼어든 실패도 알리지 않는다.
- 아래 실행에서는 뜨지 않는다. 사본 rekordbox 폴더(`DJC_REKORDBOX_DIR`)가 있어도 같다.
  - 명시한 사본(`--db`·`DJC_DB`)으로 연 창
  - 자가 테스트·측정·캡처 실행(`DiagnosticRun`)
- `DiagnosticRun`이 보는 인자는 아래와 같다.
  - `--…-selftest`
  - `--…-perf…`
  - `--…-capture(s)=`
  - `--autoplay`
  - `--reflection-layout=`
- 측정·확인 중에 90초 뒤 디스크 일이 끼지 않게 하려는 것이다. 새 개발용 인자는 이 이름 규칙을 따른다.

**설정 공유**

- 보관 일수는 CLI가 읽지 못하는 앱 UserDefaults에 있다.
- 그래서 앱이 설정을 바꿀 때와 앱을 켤 때 DJCrate 데이터 폴더의 `shared-settings.json`(`SharedSettingsFile`)에도 적는다. `djc snapshot-point`는 그 값을 따른다.

### 시점 스냅샷으로 복원 (`RekordboxWriter.restore(pointSnapshot:)`, #225)

복원 순서는 아래와 같다.

1. 대상을 확인한다(`resolveShareRoot`). 시험 프로세스의 실제 라이브러리는 거부한다.
2. rekordbox·Agent가 꺼져 있는지 본다.
3. 스냅샷의 `snapshot.json`을 읽어 확인한다.
4. `master.db`와 담았다고 적힌 항목이 링크 없는 일반 파일·폴더인지 본다.
5. 같은 라이브러리인지 본다(`djmdProperty.DBID`).
6. 스냅샷 DB의 무결성을 본다.
7. 사본 옆 파일이 라이브 파일의 링크가 아닌지 본다.
8. **복원 직전 시점 스냅샷**을 뜬다. 실패하면 아무것도 바꾸지 않는다.
9. 쓰기 전 백업 폴더에 복원 표시를 남긴다.
10. 분석·앨범아트 폴더를 대상 옆에 클론으로 준비한다(`.djc-restore-…`).
11. `master.db`·`masterPlaylists6.xml`·`playlists3.sync`를 바꾼다. `master.db` 곁의 `-wal`·`-shm`은 지운다.
12. 지금 폴더를 옆(`.djc-old-…`)으로 옮긴다. 준비한 폴더를 그 이름으로 바꾼다.
13. 다시 읽어 무결성과 라이브러리 ID를 검증한다.
14. 두 폴더의 파일 목록·크기·수정 시각이 스냅샷과 같은지 검증한다.
15. 옮겨 둔 폴더를 지운다. 남은 것을 정리한다.

- 스냅샷에 없던 폴더는 없앤다. 그 시점에 앨범아트가 없었던 경우다.
- 스냅샷에 없던 `masterPlaylists6.xml`·`playlists3.sync`는 지금 것을 둔다. rekordbox가 그 뒤 만든 파일이다.
- 바꾸는 도중 실패하면 아래처럼 되돌린다.
  - DB와 두 파일은 복원 직전 스냅샷에서 되돌린다.
  - 폴더는 옮겨 둔 지금 내용으로 되돌린다.
  - 복원 표시를 지운다.
- 그것도 못 하면 `pointRestoreFailed`로 `djc snapshot-point restore <복원 직전 ID>` 명령을 알린다.

**연쇄 복원이 필요 없는 이유**

- 스냅샷이 범위 전체를 담는다. 그래서 고른 스냅샷 하나로 DB와 분석 파일이 같은 시점이 된다.
- 쓰기 전 백업처럼 뒤 백업들의 파일을 차례로 되돌릴 일이 없다.
- 복원 직전 스냅샷도 전체를 담는다. 그것으로 다시 복원하면 분석·앨범아트 파일까지 복원 전으로 돌아온다.

**쓰기 전 백업 사슬과의 경계**

- 시점 복원은 분석 폴더를 통째로 바꾼다. 쓰기 전 백업은 그 쓰기가 바꾼 파일만 담는다.
- 그래서 시점 복원보다 옛 쓰기 전 백업은 사슬(#222)로 분석 파일을 맞출 수 없다.
- 시점 복원은 쓰기 전 백업 폴더에 `<시각>-point-restore/point-restore.json`을 남긴다. 이 파일에는 되돌린 스냅샷과 복원 직전 스냅샷의 ID가 있다.
- `RekordboxWriter.restore`는 고른 백업 뒤에 이 표시가 있으면 아무것도 바꾸지 않는다. 복원 직전 백업도 만들지 않는다.
- 대신 시점 스냅샷 창의 ‘복원 직전’ 스냅샷을 고르라고 알린다.
- 시점 복원 뒤의 쓰기 전 백업은 평소처럼 되돌린다.
- 표시는 쓰기 백업 정리(#221)에서 지운다. 그보다 옛 쓰기 백업과 함께 지운다.

**그 밖의 규칙**

- 초안은 건드리지 않는다. 초안의 `base`가 복원한 rekordbox와 맞지 않는 곡은 쓸 때 거른다.
- 앱은 차이로 바뀐 곡을 덱이 다시 읽게 한다.
- **비교**(`RekordboxPointSnapshotDiff`)
  - 두 DB를 임시 폴더에 복사해 읽는다. 스냅샷·라이브 폴더에 곁 파일을 남기지 않게 하려는 것이다.
  - 아래를 복원 방향으로 센다.
    - 곡(UUID)
    - 큐, BPM, 곡 정보
    - 재생 목록(ID)
  - 분석·앨범아트 파일은 경로, 크기, 수정 시각만 견준다.
  - `djc lab db-diff`(모든 표·칸)는 규칙을 알아내는 실험 도구다. 그래서 제품 코드로 옮기지 않았다.
- **클라우드 동기화**(#229 미확인)
  - 지금 DB의 `lastUpdateCount`가 스냅샷 때보다 크면 복원을 막지 않는다.
  - 이때 확인 창에 "클라우드 동기화가 복원한 내용 일부를 다시 바꿀 수 있습니다"를 한 줄 더한다.
- 확인 창은 하나다. 되돌릴 수 없는 외부 쓰기라 묻는다.
- CLI는 플래그가 곧 동의다.
- 시험은 `RekordboxPointRestoreTests`다. 아래를 본다.
  - 두 번 쓴 뒤 가운데 시점 복원과 복원 직전으로 다시 복원
  - rekordbox 켜짐·다른 라이브러리·망가진 스냅샷 거부
  - 검증 실패 되돌림
  - 쓰기 전 백업 사슬 경계
  - 복원 직전 3개 보존
  - 실제 라이브러리 거부
  - 차이 요약·클라우드 흔적

## 새 쓰기 경로를 여는 방법

1. 사용자에게 rekordbox에서 그 편집을 직접 해 달라고 부탁한다. 곡 이름을 받는다.
2. 편집이 끝나면 사용자가 rekordbox를 종료한다.
3. 새 스냅샷을 뜬다(`djc snapshot --force`).
4. 편집 전 스냅샷과 새 스냅샷을 비교한다. `djc lab sql <사본> "…"`·`djc lab db-diff`를 쓴다.
5. 바뀐 테이블·칸과 usn 순서를 본다.
   - rekordbox가 조작마다 바로 쓰는 표면 rekordbox를 켜 둔 채 단계마다 떠서 비교할 수 있다.
   - 명령은 `djc lab playlist-watch --out <폴더>`다. 읽기 전용 복사만 한다.
6. 실험 전 사본에 DJCrate로 같은 편집을 쓴다. 칸마다 비교한다.
   - 예: `djc lab loop-repro --old … --new … --ids … --work <임시 폴더 아래>`
7. 일치하면 `Tests/RekordboxKitTests`에 골든 테스트를 먼저 쓴다.
8. 막아 둔 조건을 푼다.
9. 이 문서에 규칙을 적는다.
